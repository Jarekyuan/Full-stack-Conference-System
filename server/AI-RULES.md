# AI 协作规则（全工具通用）

> 本文件是当前项目所有 AI 助手（Copilot / Claude Code / Codex 等）的通用协作规则。
> 规则基于维护者的全局协作规则（`~/.claude/CLAUDE.md`，Global Instructions），并按本项目做了适配与补充。
> 各工具入口文件（`CLAUDE.md`、`AGENTS.md`）统一引用本文件，项目内规则正文只在此处维护，请勿在入口文件中重复。

## 需求澄清规则

当任务不明确、需求模糊、或涉及方案选择时，遵循以下流程：

1. 先向用户提问，**一次只问一个**
2. 根据用户的回答持续追问
3. 直到有 **95% 的信心**完全理解用户的真实需求和目标时，再给出最终方案

**适用场景**：需求描述模糊、有多种可行方案、用户未指定关键细节、任务影响范围大。

**跳过条件**：任务明确、细节充分时（如修正拼写错误、明确的小改动等）可直接行动，无需追问。

## 会话交接规则

当会话即将结束时（用户主动要求、任务暂告段落、或上下文将满），写一份交接文档保存为 `HANDOFF.md`，内容包括：

1. **当前任务**：我们在做什么，目标是什么
2. **已完成**：已经完成了哪些具体工作
3. **卡点/阻塞**：当前卡在哪里，遇到了什么问题
4. **下一步计划**：后续的计划和待办事项
5. **踩过的坑**：已经踩过哪些坑，绝对不要再重复踩

**写作原则**：写给一个完全没有上下文的新会话看，确保新会话能无缝接手。

## 测试节奏规则

**默认不跑全量测试**（本项目指：全模块 `mvn test`、`mvn clean verify`（含 JaCoCo 覆盖率）、`mvn checkstyle:check` + `spotbugs:check` + `pmd:check` 静态检查全套等一次性跑完的验证），效率低且浪费 token。测试按节奏分批：

- **开发过程中**：只针对本次修改运行最相关的定向测试（如 `mvn test -pl meeting-api -am -Dtest="com.xxx.XxxTest" -Dsurefire.failIfNoSpecifiedTests=false`）；纯文档、注释、文案类修改不必测试。
- **中途发现测试失败**：定位、修复、重跑**受影响的那部分**即可，不必每次都从头跑全量。
- **全量测试只在两种情况下进行**：
  1. 用户**主动要求**；
  2. 你判断本次修改**影响范围过大**（跨模块、动了公共接口/核心算法、改动面广到定向测试覆盖不住）——这种情况**也必须先问过用户**再跑。
- **“功能完成/交付前”不构成跑全量的理由**：先交付、先让用户看效果；要不要全量回归由用户决定。
- 任何一次全量之前都要先询问用户并说明理由（改了什么、为什么要全量、大概耗时），得到同意再执行。

## 文档维护规则

**任务/对话完成后及时更新文档**：工作一旦完成或告一段落，立即把相关文档（方案、进度、规则、`HANDOFF.md` 等）更新到与现状一致，不遗留过期描述。

**无效内容及时删除**：已废弃的方案、被推翻的结论、过时的临时说明等无效内容，及时从文档中删除（需要留痕的先归档），不要让它持续累积。

**目的**：保持文档精简、准确、可维护；避免过期、冗余内容过多占用上下文（尤其 AI 会话上下文），拖慢后续协作。

## 代码质量规则

写代码时始终注意代码质量，**禁止产出“屎山”代码**：

- **非空校验先判断必要性**：添加非空（null / 空集合 / 空串）校验前，先确认此处是否真的可能为空（上游是否已保证、类型是否已约束、调用链是否确定）；没有必要就不加，不要为了“保险”无脑判空。
- **不要不必要的换行**：能一行写完的就一行写完；只有当一行代码超出编辑器窗口显示宽度时，才进行换行。
- **禁止写出屎山代码**：不堆砌重复逻辑、不写超深嵌套和超长方法、不用含糊命名；新代码应当清晰、直白、可维护。
- **不要模仿存量屎山代码**：若周边存量代码已是屎山（重复、深嵌套、坏味道），不要照抄它的写法；按本规则编写新代码，必要时先把改动范围内的逻辑理清。

## 判空与工具类规则

**判空与常用工具优先使用现成的 JDK / Hutool，不要自己造轮子**：

- **对象判空**：`java.util.Objects`（`Objects.isNull / nonNull`、`Objects.equals`、`Objects.requireNonNull`）。
- **集合 / Map 判空**：Hutool `CollUtil.isEmpty / isNotEmpty`（Collection、Map 通用）。
- **字符串判空**：Hutool `StrUtil.isBlank / isNotBlank`（本项目亦可用 `CharSequenceUtil`、`org.springframework.util.StringUtils.hasText`）。
- **数组判空**：Hutool `ArrayUtil.isEmpty / isNotEmpty`。
- **禁止手写**：`x != null && !x.isEmpty()`、`list == null || list.size() == 0` 这类重复判断；能用工具方法表达的一律用工具方法。
- **先查再写**：需要工具能力时，先搜项目 / 依赖（JDK、Hutool、Spring）里是否已有现成方法，再决定是否新增。

## 三方工具优先规则（实现功能）

**实现功能时，优先考虑成熟的三方工具 / 组件，不要自己硬写**：

- **动手前先调研**：需要的能力是否已有成熟方案 —— 先看项目已引入的依赖，再看社区事实标准（Apache / Google / Spring / Hutool 等）。
- **不要手写基础轮子**：解析、序列化、HTTP 客户端、重试、调度、加解密、日期时间等本可由成熟库承担的逻辑，不自己硬写。
- **新增依赖要克制**：引入新依赖前先确认项目内是否已有同类能力、维护活跃度与安全记录是否可接受；能用已有依赖实现的不新增依赖。
- **自研要有理由**：仅当三方方案确实不满足（业务特有逻辑、性能 / 安全硬约束）才自研，并在代码或提交说明中写明原因。

## 注释规范规则

**注释要克制、要为人而写**：

- **不要无限制地添加注释**：只在代码本身说不清的地方写（为什么这么做、业务背景、非直觉的约束或坑）；一眼能看懂的代码不加注释，更不要逐行给代码“配音”。
- **注意注释质量**：写清“为什么”而不是复述“做了什么”；不写无信息量的注释（如在 `setName(...)` 上写“设置名称”），也不留与代码不符的过期注释。
- **站在人的角度写**：以读者（同事、后续维护者）的视角组织语言，用词具体、不自造缩写和含糊表述；写完后自己读一遍，确认别人能看懂。
