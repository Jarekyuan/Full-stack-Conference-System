# AI 协作规则（server/ 后端 · 全工具通用）

> 本文件是**后端（server/）目录**下所有 AI 助手（Claude Code / Codex / Copilot 等）的协作规则。
> 规则基于维护者的全局协作规则（`~/.claude/CLAUDE.md`，Global Instructions），并按**本项目（会议室预约系统）**做了适配与补充。
> 各工具入口文件（`CLAUDE.md`、`AGENTS.md`）统一引用本文件，规则正文只在此处维护，请勿在入口文件中重复。

---

## 一、项目真相源（防幻觉第一原则）

**写任何代码前，先找到它在文档里的出处。文档是唯一事实来源，不许凭记忆或"常见写法"臆造。**

| 你要做什么 | 先读哪里（真相源） |
|-----------|------------------|
| 接一个新任务 | `docs/05-开发计划.md` 对应任务（T 编号，五要素：目标/文件/实现/验收/验证命令） |
| 数据库相关 | `docs/03-数据库设计.md`（表/字段/索引）+ `db/01-schema.sql`（以 DDL 为准） |
| 写接口 | `docs/04-接口设计.md`（路径/请求/响应/错误码——**不许自创字段名和路径**） |
| 状态值/角色/枚举 | `docs/04-接口设计.md` 第五章 + `docs/03` 字段注释 |
| 架构/技术选型/降级策略 | `docs/02-技术架构方案.md` |
| 业务规则拿不准 | `docs/01-需求文档.md`（含 R-1~R-15 业务规则） |

**铁律**：

1. 文档与代码冲突时：**停下，报告冲突**，用户确认后先改文档、再改代码；
2. 文档没写的细节：不自作主张，列出选项问用户；
3. 不发明不存在的：字段、接口、错误码、配置项、依赖版本；
4. 任务完成的标准 = 05 文档该任务的"验收标准"全勾选 + "验证命令"**实际执行通过**。

## 二、技术栈基线（版本以此为准，不许擅自升级/降级/换框架）

- JDK **17**（不是 8/11/21/24）；**jakarta.*** 命名空间（不是 javax）
- Spring Boot **3.2.x** / Spring Cloud **2023.0.x** / Spring Cloud Alibaba **2023.0.x**
- Spring Security **6.x**（`SecurityFilterChain` 新式写法，不用已废弃的 `WebSecurityConfigurerAdapter`）
- MyBatis-Plus **3.5.x**；MySQL **8.0**；Redis 7 + **Redisson**；RabbitMQ **3.13**
- Nacos 服务端 **2.4.2**（注册 + 配置中心）；接口文档 springdoc-openapi
- 工具：Lombok、Hutool、Jackson（时间格式统一 `yyyy-MM-dd HH:mm:ss`）
- 一个系统一个拆法：`meeting-common / gateway / auth-service / meeting-service / notification-service`（拆分依据见 02 文档 2.1）
- 需要变更版本或引入新框架时：**先问用户，并同步更新 02 文档第八章**。

## 三、工程结构与命名约定

```
server/
├── pom.xml                 # 父 POM（统一版本管理）
├── meeting-common/         # 共享：Result / PageResult / ErrorCode / BusinessException / JwtUtil / UserContext
├── gateway/                # :8080  路由 + JWT 校验 + 头注入
├── auth-service/           # :8081  认证与用户
├── meeting-service/        # :8082  会议核心（预约/审批/状态机/定时任务）
└── notification-service/   # :8083  通知（MQ 消费 + WebSocket）
```

- 包名：`com.smt.common` / `com.smt.gateway` / `com.smt.auth` / `com.smt.meeting` / `com.smt.notification`
- 服务内分层：`controller / service(+impl) / mapper / entity / dto(入参) / vo(出参) / config / aop / task / mq / feign`
- 命名：接口 `I*Service` + 实现 `*ServiceImpl`；`*Mapper`；Controller 根路径用业务域复数（`/meetings`、`/rooms`）
- **entity 绝不直接返回前端**：入参用 DTO、出参用 VO（防越权与信息泄露）

## 四、关键全局约定（跨模块契约）

- **统一响应** `{code, msg, data}`：code=0 成功；业务错误用错误码（段位：1xxxx 通用 / 2xxxx 认证 / 3xxxx 会议室 / 4xxxx 预约 / 5xxxx 审批 / 6xxxx 通知 / 7xxxx 会议纪要与文件，全表见 04 文档第二章）
- **错误码必须登记在 `ErrorCode` 枚举**，不许散落魔法数字；新增码同步登记 04 文档表
- **会议状态值**：10 待审批 / 20 已预约 / 30 进行中 / 40 已结束 / 50 已取消 / 60 已拒绝
- **状态变更必须走状态机**（`MeetingStateMachine.transition`：校验迁移 + 写 `meeting_status_log`），禁止裸 UPDATE 改状态
- **认证链路**：网关验 JWT → 注入 `X-User-Id`/`X-User-Roles`（**逗号分隔多角色**，v1.3）→ 服务内从 `UserContext` 取用户；服务内不许自己解析 token
- **角色数据（v1.3）**：角色走 RBAC 五表（`sys_user_role` 关联，一人可多角色），**禁止在用户表加角色字段或代码里硬编码单角色**；鉴权一律 `@PreAuthorize("hasRole('ADMIN')")`（多角色任一匹配即通过）；部门（`sys_dept`）仅作组织结构，不参与鉴权
- **并发锁**：预约用 Redisson（key=`lock:meeting:{roomId}:{yyyyMMdd}`，见 02 文档 5.2）；修改会议用乐观锁 version；审批用 `SELECT ... FOR UPDATE` 锁会议行
- **本地配置**：真实密钥只进 `application-local.yml`（已被 .gitignore 忽略）；可提交的配置用占位符
- **端口**：gateway 8080 / auth 8081 / meeting 8082 / notification 8083

## 六、任务执行工作流（vibe coding 会话节奏）

1. **认领任务**：从 `docs/05-开发计划.md` 取当前 T 编号任务——**一次一个，不跳步、不合并大改**；
2. **读真相源**：先读该任务所需的上游文档章节（如 T2.6 → 02 的 5.2 + 03 的 4.1），再动笔；
3. **声明计划**：动手前列出改动文件清单与要点（改动超过 50 行时必须等用户确认）；
4. **小步实现**：只动任务"涉及文件"范围内的文件；确有必要超范围时先说明原因；
5. **跑验证命令**：执行任务自带的验证命令，贴**真实输出**——不许说"应该能通过"；
6. **收尾**：勾选验收标准 → 提交（`git commit -m "feat(T2.6): xxx"`，遵循 Conventional Commits）→ 报告结果与下一步。

## 七、需求澄清规则

当任务不明确、需求模糊、或涉及方案选择时，遵循以下流程：

1. 先向用户提问，**一次只问一个**
2. 根据用户的回答持续追问
3. 直到有 **95% 的信心**完全理解用户的真实需求和目标时，再给出最终方案

**适用场景**：需求描述模糊、有多种可行方案、用户未指定关键细节、任务影响范围大。

**跳过条件**：任务明确、细节充分时（如修正拼写错误、明确的小改动等）可直接行动，无需追问。

## 八、会话交接规则

当会话即将结束时（用户主动要求、任务暂告段落、或上下文将满），写一份交接文档保存为 `HANDOFF.md`，内容包括：

1. **当前任务**：我们在做什么，目标是什么
2. **已完成**：已经完成了哪些具体工作
3. **卡点/阻塞**：当前卡在哪里，遇到了什么问题
4. **下一步计划**：后续的计划和待办事项
5. **踩过的坑**：已经踩过哪些坑，绝对不要再重复踩

**写作原则**：写给一个完全没有上下文的新会话看，确保新会话能无缝接手。

## 九、测试节奏规则

**默认不跑全量测试**（指 `mvn test` 全模块一把梭），效率低且浪费 token。测试按节奏分批：

- **开发过程中**：只针对本次修改运行最相关的定向测试（如 `mvn -pl meeting-service test -Dtest=ConflictCheckerTest`）；纯文档、注释、文案类修改不必测试。
- **中途发现测试失败**：定位、修复、重跑**受影响的那部分**即可，不必从头跑全量。
- **全量测试只在两种情况下进行**：
  1. 用户**主动要求**；
  2. 你判断本次修改**影响范围过大**（跨模块、动了公共接口/核心算法）——这种情况**也必须先问过用户**再跑。
- **"功能完成/交付前"不构成跑全量的理由**：先交付、先让用户看效果；要不要全量回归由用户决定。
- **但 05 文档任务自带的"验证命令"一条都不能省**——它是任务的验收关口（进度慢一点没关系，验收必须实打实）。

## 十、文档维护规则

**任务/对话完成后及时更新文档**：工作一旦完成或告一段落，立即把相关文档（方案、进度、规则、`HANDOFF.md` 等）更新到与现状一致，不遗留过期描述。

**无效内容及时删除**：已废弃的方案、被推翻的结论、过时的临时说明等无效内容，及时从文档中删除（需要留痕的先归档），不要让它持续累积。

**目的**：保持文档精简、准确、可维护；避免过期、冗余内容过多占用上下文（尤其 AI 会话上下文），拖慢后续协作。

## 十一、数据访问规范（手写 MyBatis 为主）★

**目标：练 SQL 功底。SQL 一律手写，不依赖 ORM 的"便利方法"。**

- **Mapper 接口 + XML 手写 SQL**：每张表一个 XML（`resources/mapper/`），显式 `<resultMap>`（不靠自动映射的侥幸）；联表、统计等复杂查询一律写在 XML。
- **动态 SQL 用标签**：`<where>` / `<if>` / `<choose>` / `<foreach>` / `<set>`；禁止用 Wrapper 拼条件。
- **分页手写**：`LIMIT #{offset}, #{size}` + 独立 `COUNT(*)` 查询（两条 SQL 都要写；顺带理解深分页优化）。
- **参数一律 `#{}`**（预编译防注入）；`${}` 仅限不可参数化的结构（如表名/排序字段白名单），且**必须注释说明**。
- **JSON 列**用自定义 `JsonTypeHandler`（Jackson 实现），在 XML resultMap 中引用——不依赖 MP 的 TypeHandler。
- **复杂 SQL 注释预期索引**：如冲突检测 SQL 标注"预期命中 idx_room_time"（呼应 docs/03 第四章）。
- **公共字段**（created_at/updated_at）：由 SQL 显式赋值或数据库默认值处理（表已配 `DEFAULT CURRENT_TIMESTAMP`），不引入自动填充框架。

**MyBatis-Plus 使用限制**（依赖保留在父 POM，但默认不用）：

- 仅当"手写 SQL 确实不值得"的特殊场景可用（如一次性数据修复脚本、非业务链路的批量操作），**且必须向用户说明原因、经确认后使用，并在代码注释中写明理由**；
- 写法示例（注释必须写明"为什么用 MP 而不是手写"）：

```java
// 数据修复脚本：按主键批量更新 500 条历史数据（非业务链路，逐条手写无价值）
// 经确认使用 MyBatis-Plus 的 updateBatchById 替代手写 foreach；业务代码仍一律手写 XML
// meetingMapper.updateBatchById(list);
```

- AI 执行任务时：**先给出手写 XML 方案**；若认为确实该用 MP，停下来向用户说明并等待确认。

## 十二、代码质量规则

写代码时始终注意代码质量，**禁止产出"屎山"代码**：

- **非空校验先判断必要性**：添加非空（null / 空集合 / 空串）校验前，先确认此处是否真的可能为空（上游是否已保证、类型是否已约束、调用链是否确定）；没有必要就不加，不要为了"保险"无脑判空。
- **不要不必要的换行**：能一行写完的就一行写完；只有当一行代码超出编辑器窗口显示宽度时，才进行换行。
- **禁止写出屎山代码**：不堆砌重复逻辑、不写超深嵌套和超长方法、不用含糊命名；新代码应当清晰、直白、可维护。
- **不要模仿存量屎山代码**：若周边存量代码已是屎山（重复、深嵌套、坏味道），不要照抄它的写法；按本规则编写新代码，必要时先把改动范围内的逻辑理清。

## 十三、判空与工具类规则

**判空与常用工具优先使用现成的 JDK / Hutool，不要自己造轮子**：

- **对象判空**：`java.util.Objects`（`Objects.isNull / nonNull`、`Objects.equals`、`Objects.requireNonNull`）。
- **集合 / Map 判空**：Hutool `CollUtil.isEmpty / isNotEmpty`（Collection、Map 通用）。
- **字符串判空**：Hutool `StrUtil.isBlank / isNotBlank`（亦可用 `CharSequenceUtil`、`StringUtils.hasText`）。
- **数组判空**：Hutool `ArrayUtil.isEmpty / isNotEmpty`。
- **禁止手写**：`x != null && !x.isEmpty()`、`list == null || list.size() == 0` 这类重复判断；能用工具方法表达的一律用工具方法。
- **先查再写**：需要工具能力时，先搜项目 / 依赖（JDK、Hutool、Spring）里是否已有现成方法，再决定是否新增。

## 十四、三方工具优先规则（实现功能）

**实现功能时，优先考虑成熟的三方工具 / 组件，不要自己硬写**：

- **动手前先调研**：需要的能力是否已有成熟方案 —— 先看项目已引入的依赖，再看社区事实标准（Apache / Google / Spring / Hutool 等）。
- **不要手写基础轮子**：解析、序列化、HTTP 客户端、重试、调度、加解密、日期时间等本可由成熟库承担的逻辑，不自己硬写。
- **新增依赖要克制**：引入新依赖前先确认项目内是否已有同类能力、维护活跃度与安全记录是否可接受；能用已有依赖实现的不新增依赖。
- **自研要有理由**：仅当三方方案确实不满足（业务特有逻辑、性能 / 安全硬约束）才自研，并在代码或提交说明中写明原因。

## 十五、注释规范规则

**注释要克制、要为人而写**：

- **不要无限制地添加注释**：只在代码本身说不清的地方写（为什么这么做、业务背景、非直觉的约束或坑）；一眼能看懂的代码不加注释，更不要逐行给代码"配音"。
- **注意注释质量**：写清"为什么"而不是复述"做了什么"；不写无信息量的注释（如在 `setName(...)` 上写"设置名称"），也不留与代码不符的过期注释。
- **站在人的角度写**：以读者（同事、后续维护者）的视角组织语言，用词具体、不自造缩写和含糊表述；写完后自己读一遍，确认别人能看懂。
