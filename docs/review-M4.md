## Required（全部已修）

### R1 MQ 幂等标记与 ACK 的交互：崩溃后消息**静默丢失** + 两处注释与事实相反

`notification-service/.../mq/MeetingEventConsumer.java`（原 76-100 行）+ `ConsumeIdempotency.java`

**问题**（两个方向都错）：
1. **IN_FLIGHT 一律 ack 丢弃** → 消费中进程被 kill（OOM/发版/优雅停机超时），broker 立刻重投，
   新进程看到 P（TTL 10 分钟没过期）→ 判"正在处理中"→ ack 丢弃 → **这条通知永远不会生成**，
   而日志写着"重复投递，已丢弃"，看着完全正常。类注释却写"进程崩溃时重投回来还能重新处理（P 已过期）"
   ——**与自己的 TTL 自相矛盾**（重投在几秒内到达）。
2. **成功路径的 `basicAck` 在业务 catch 里** → ack 抛异常（连接刚断）会走进"业务失败"分支：
   先把刚写的"已处理"标记删掉，随后消息被重投 → 标记没了 → **重复发一遍通知**。

**修法（⚠️ 我第一版改错了方向，第二版才对——留痕）**：
- **第一版（错）**：只去掉 P 状态、标记仍写在**处理之前**。这**没有解决任何问题**——
  崩溃时标记已经写下了，重投照样被当成重复而 ack 丢弃，后果与 P 状态**完全一样**，只是少了一个状态。
  是评审 agent 追问"P 与 S 的区别到底在哪"时我才发现方向错了。
- **第二版（对）：标记写在**成功之后**（mark-after-success）**：
  ```
  已处理？ ──是─▶ ack（重复投递，丢弃）
     │否
  处理（重试 3 次）─失败─▶ nack 进死信（**不写标记** → 重放死信时能重新处理）
     │成功
  写"已处理"标记 ─▶ ack（ack 若失败：标记已在 → 重投被正确判为重复，不重复发通知）
  ```
  这样三种窗口**同时**正确：崩溃在处理中 → 无标记 → 重投重新处理（**不丢**）；
  ack 失败 → 有标记 → 重投被挡（**不重**）；业务失败 → 无标记 → 死信重放可处理 ✓。
  代价只剩"极少数并发重复"（同一 msgId 两份同时被处理且都成功）——它换掉的是"崩溃后必丢"，
  取舍写死：**宁可重复一条通知，不可静默丢失**。
- **业务失败与 ack 分开**：只有业务处理（含重试）失败才 nack；ack 单独 try，失败只告警。
  顺带**`release()` 整个消失了**——"失败撤销标记"这一步在 mark-after-success 下本来就不需要。
- **并发度保持 1**（评审曾建议提到 2 以避免"毒消息退避占住全部队列"）：**单消费者 ⇒ 同队列串行 ⇒
  同一 msgId 的两份投递必然先后到达**，mark-after-success 因此没有并发窗口、去重是**确定性**的；
  提到 2 会让同队列两条并发消费同一 msgId 双双处理，与"重发不重复插入"的承诺冲突。
  取舍：确定性去重 > 那点吞吐（通知量本来就小）。

### R2 日历缓存失效覆盖不全：**延长/结束完全没发事件**；改期换房只删了新 key

`meeting-service/.../service/AvailabilityService.java` + `MeetingReserveService.java`

**问题**：`extend()` / `finish()` 不发任何领域事件（缓存监听收不到）；`updated` 事件只带**新** roomId/时间，
`evictWeeks` 只删新房间/新周 → **旧房间的日历会一直挂着一场已经搬走的会**。
而 `AvailabilityService` 的注释把延长/结束列进"写路径…事件是统一出口"的清单里——**又是一条与事实相反的注释**。

**修法**：
- 抽出 `CalendarCacheEvictor`（"按房间+时段删周缓存"只有一份实现）；
- `update()` 成功后就地补删**旧**房间/旧时段（Cache-Aside 的先更库后删缓存）；
- `extend` / `finish` 补发 `updated` 事件（结束时间变了、状态变 40 了都是日程变化）；
- 注释里的"已知缺口"从一类扩成两类（改期旧 key 由就地调用补上；定时任务 20→30/40 仍不发事件，属已知取舍）。
- **补了验证**：`verify-m4-cache.sh` 新增"把会议从 4 号房改到 6 号房 → 4 号房该周缓存必须消失"。

### R3 前端：**token 过期后的重连永远失败且静默**

`web/src/hooks/useWebSocket.ts`

**问题**：`connect()` 里"现取 token"拿走的是**过期的那个**——本地 token 刷新只有一处触发点
（HTTP 401 拦截器），而 WS 是长连接、闲置 >30 分钟后重连不会经过任何 REST 请求。
结果是无限退避重试 + 角标静默停更（表现为"最近没人找我"，而不是报错）。
浏览器的 WebSocket API **读不到握手失败的 HTTP 状态码**，所以"失败后再刷新"这条路走不通。

**修法**：`scheduleReconnect` 里**先发一次 REST**（`refreshUnread`）再连——
那次请求会走 401 拦截器触发无感刷新（刷新失败自动跳登录），顺带把断线期间漏掉的未读变化补齐。
⚠️ 这个洞 e2e 永远测不到（脚本只把服务停 ~1 分钟，token 全程有效）——已写进注释。

## Optional（修了 9 条）

- **并发脚本的"临时关限流"三步都可能静默失效**（curl 不看返回码就打印"已关闭"；只挂 EXIT trap，
  SIGTERM 会把限流**留在关闭状态**；同一段 20 行在两处复制）→ 抽成 `scripts/lib/ratelimit.sh`：
  **读回确认**（不成就退出）、EXIT/INT/TERM 都挂、**链式 trap**（不覆盖调用脚本自己的清理）。
- **限流脚本"6 次全部放行"只断言"没有 10005"** → 改成断言 code 分布（每发 0 或 40001，且至少一发为 0）。
- **消费脚本用固定 `sleep 3` 验幂等** → 改成等**证据日志**（"重复投递，丢弃"）出现。
- **前端已读操作无错误处理**（点一下没反应 + unhandled rejection；docs/04 明确要求 60001 静默 + 刷新）→ 补 try/catch。
- **登出不清未读角标** → `userStore.logout` 里 reset。
- **REST 与 WS 两个权威值互相覆盖**（全部已读后 REST 的旧响应会把 WS 的新值盖回去）→ store 加 `version`，
  REST 落地前比对，期间被 WS 写过就丢弃。
- **两个老 e2e 的清理只在成功路径** → 挪进 `finally`（`e2e-notify-center` 之前的教训没推广到老朋友身上）。
- **审计切面在失败时把"组织人 id"记成 target**（`create(dto, organiserId)` 的第一个 Long 是组织人）→
  `@Log` 加 `targetFromResultOnly`，创建类失败记 `-`（宁可缺字段，不可记错 id）。
- **两个切面的顺序没有声明**（靠 bean 名碰巧成立，而 docs/05 已把顺序写进说明）→ 显式 `@Order`：
  `审计(+10) → 幂等(+20) → 限流(+30) → 事务`（重复提交不该消耗防刷额度）。
- **`publisher-confirm-type: correlated` 达不到注释宣称的效果**（没注册回调，nack 与"路由不到队列"依然静默）→
  注册 `ConfirmCallback` / `ReturnsCallback`（"消息静默消失"变成日志 ERROR）+ `publisher-returns: true`。
- **WS 推送体 `createdAt` 恒为 null**（insert 靠列默认值，推送用的是同一批内存对象）→ 服务显式赋时间并写进 SQL。
- **`MeetingEventConsumer` 的并发注释不准确**（6 个队列在一个监听器上，默认一条线程消费全部；
  "分开队列就不会互相堵"不成立）→ 修正注释 + `concurrency: 2`（一条毒消息不再占住全部队列）。

## 明确不修（记在这，别当成已完成）

1. **重试预算只有约 1.5 秒 + DLQ 无消费者、无告警**：持续 >1.5s 的后端故障会把消息一次性推进死信。
   要真稳得加"延迟重投消费者"或"DLQ 深度告警"——属可靠性增强，本轮不做（docs/05 里也没要求）。
2. **`acquire()` 在 try 之外**：Redis 挂掉时会让消费容器反复重启（消息不丢，靠重投）。
   这是**有意**的取舍（幂等是正确性前提，不像限流那样"异常放行"），但注释里没写明——已补。
3. **WS 会话表在单进程内存里**：多实例部署时 A 实例的通知推不到连在 B 实例上的用户。
   单实例部署下不成立，docs/02 5.6 已记；真上多实例要外置（Redis pub/sub 或粘性路由）。

### 修复过程中新踩的坑（都已落进 CLAUDE.md 与脚本注释）

1. **`mvn clean` 会把"正在跑的服务所依赖的 jar"删掉**：正在运行的 JVM 不会立刻死，
   但懒加载的 jar 内资源（ServiceLoader）会崩 → auth 接口 500；且"按端口 kill 再按 jar 路径重启"
   的脚本再也起不来。表象是"整轮 13 项验证全红"，根因却与业务无关。
   **规矩：构建+单测 → (重)启动服务 → 跑脚本，中途绝不再 clean/构建。**
2. **T4.8 的限流把"其它"验证脚本打挂了**：它们为验证别的功能会连发多次预约、同一个用户 → 撞 10005，
   报出来却是"创建失败 code=10005"，看着像功能坏了。之前只给两个并发脚本做了限流开关，
   **没推广到全部**——现已抽成 `scripts/lib/ratelimit.sh` + `web/e2e/lib/ratelimit.cjs`，
   所有"会造会"的脚本（9 个 bash + 5 个 e2e）开头统一关掉、退出恢复（含**读回确认**与**链式 trap**）。
3. **"回查库"的断言必须确认自己在清理之前执行**：T4.6 e2e 里我把新断言插到了"收尾自清理"之后，
   于是查出来永远是空 ✗——为了追这个"谁在删通知"，我开了 MySQL general log、又做了实时旁观，
   最后发现是**断言的位置**问题。教训：这类断言失败时，先看它在脚本里的**位置**，再怀疑产品。
4. **`book()` 之类的小助手，参数静默忽略最坑**：`verify-m4-notify-api.sh` 的 `book()` 没有"参会人"分支，
   传进去的第 6 个参数被无声丢掉 → "给 user2 造未读"那段其实造了一场没有参会人的会，
   取消通知自然发不出去。排查耗时仅次于第 3 条。
