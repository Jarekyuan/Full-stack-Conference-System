## 一、项目背景与目标

### 1.1 项目是什么

一个**前后端分离的企业会议室预约系统**（简化重构版），从真实企业系统（原公司会议室管理平台）中提炼核心业务链路重新设计实现。

- **后端**（重点）：Java + Spring Boot + MySQL + Redis，独立开发
- **前端**（次要）：React，能用、能演示全流程即可
- **对标物**：原公司 `virsical-meeting`（前端） + `smartmeeting`（后端），但**只提炼精华，不复刻**

### 1.2 为什么做这个项目（三重目标）

| 目标       | 说明                                                                              |
| -------- | ------------------------------------------------------------------------------- |
| ① 后端熟练化  | 用一套真实业务把 Java 后端知识**串起来用一遍**：分层架构、MyBatis-Plus、Redis 缓存、分布式锁、状态机、定时任务、事件驱动、消息通知 |
| ② 全栈闭环   | 前后端分离完整走一遍：接口设计 → 联调 → 部署，补齐"没独立部署过项目"的短板                                       |
| ③ 面试主线项目 | 一个能让面试官听 15 分钟不打断的项目：有并发场景、有技术选型、有踩坑叙事、有"我为什么这么设计"                              |

### 1.3 与原系统的关系：提炼 ≠ 复刻

原系统是**企业级生产代码**：后端 2881 个 Java 文件 / 44 万行、前端 69 个业务页面，包含多租户、10+ 第三方平台对接、IoT 设备、日历双向同步、计费等大量模块。

新项目**只做减法不做加法**：

- ✅ 保留：能讲清楚、能深挖、闭环完整的核心流程
- 🔶 简化：保留骨架、砍掉分支复杂度
- ❌ 砍掉：复杂度高但面试讲不出彩的部分（详见第三章）

### 1.4 设计原则

1. **每个模块必须有一个可深挖的技术点**——拒绝纯 CRUD 堆砌（做了 10 个 CRUD 模块，不如 1 个 "并发预约冲突" 讲得深）
2. **业务闭环完整**——能完整演示：预约 → 审批 → 进行中 → 结束 / 取消 全生命周期
3. **复杂度可渐进**——分 P0/P1/P2 三档实现，每档都能独立运行、独立讲述

### 2.2 前端业务梳理

#### 2.2.1 业务模块地图（69 个页面 → 5 大模块）

| 模块          | 页面                                                         | 核心功能                           | 复杂度   |
| ----------- | ---------------------------------------------------------- | ------------------------------ | ----- |
| **日历与预约**   | Calendar / MeetingBooking / MeetingDetail                  | 周/日视图排期、预约表单（含周期会议、访客、签到）、会议详情 | ★★★★★ |
| **会议列表与管理** | MeetingList / MeetingApproval / SvcApproval / BorrowManage | 表格列表、座位视图、三类审批（会议/服务/设备）       | ★★★★  |

#### 2.2.2 预约前端完整流程（核心链路）

```
入口 1：日历页顶部「预订会议」按钮
入口 2：日历空格子点击（带房间+时间上下文）
  ↓ history.replace('/meeting/calendar/booking')
预约页（Tab 外壳：Step1 主表单 / Step3 服务 / Device 设备 / Step2 成功弹窗）
  ↓ 提交链（4 层方法串联）：
  bookMeeting()（前置校验）
   → doReserve()（参会人去重 + Exchange 授权探测）
    → continueBooking()（模式判断）
     → submitMeeting()（payload 组装，几十个字段）
  ↓ dispatch → dva model（meetingBooking/submitMeetingInfo）
  ↓ POST /smt-meeting/meeting-info/reserve
  ↓ 成功 → Step2 Modal；失败 → 按 msg 数字码弹不同对话框
```

**值得注意的前端设计**（可作为新前端参考）：

- **实时忙闲查询**：时间/房间/参会人变更 → 防抖查询（房间 500ms、参会人 1000ms）→ 前端标红提示（`room-info/scheduler`、`meeting-user/scheduler/web`）
- **日历渲染**：周视图 = 会议室列表 × 时间块网格；日视图 = 横向时间轴 + 鼠标拖拽框选；可预约性由 `checkRoomStatus()` 统一判定（维护中/节假日/预约窗口外 → 置灰）
- **状态轮询**：房间占用状态 30 秒轮询刷新（`room-info/findAllRoomState`）

#### 2.2.3 前端痛点（重构动机素材）

1. `Step1/index.js` 约 **10900 行**巨型组件，提交链绕 4 层
2. 错误处理靠**几十个 msg 数字码**逐个弹窗（强后端耦合）
3. 本地/共享租户双份配置逻辑到处复制（`isShareForUser ? shareSysModule : sysModule`）
4. 日视图混用 **jQuery 直接操作 DOM**
5. 日历数据用 30s 轮询而非 WebSocket（其实有 WS 能力）

### 2.3 后端业务梳理

#### 2.3.1 后端全景与模块划分

10 个模块（8 个在主 POM + relay/tools 独立）：`common`（公共库）→ `meeting-base`（领域模型）→ `meeting-core`（核心业务 20 万行）→ `meeting-api`（82 Controller + 46 MQ Receiver）→ `meeting`（启动）；外加 `syncmeeting`（日历同步）/ `infrared`（红外 IoT）/ `report`（报表）三个独立服务。

**技术栈**：Spring Cloud（Eureka/Config/OpenFeign）+ MyBatis-Plus + Redis/Redisson + RabbitMQ/RocketMQ/MQTT + Undertow。

#### 2.3.2 预约主链路（后端最核心，必读）

```
POST /meeting-info/reserve
  ├─ 过滤器链：XssFilter → TenantFilter（租户）→ ReserveLimitFilter（限流）
  ├─ MeetingInfoController.reserve()       ← Redisson 分布式锁（防抢单）+ @PreAuthorize + @Log
  ▼
ReserveMeetingEvent.executeEvent(vo)       ← 模板方法（BaseMeetingEvent）
  ├─ currentEvent(vo)   → 判定实际事件类型（RESERVE/APPLY/UPDATE/MODIFY/SYNC_APPLY）
  ├─ preExecute(vo)     → 组装上下文 + 三层校验 + 写库前置         ★ 校验在这里
  ├─ publishEvent(BEFORE) → 各 Operator 执行 beforeEvent
  ├─ execute()          → 真正落库（会议/参会人/会议室关联）
  └─ publishEvent(AFTER)  → 各 Operator 按 @Order 执行 afterEvent  ★ 副作用在这里
       @Order(0) 状态机 / 服务项
       @Order(1) 计费 / 资源设备
       @Order(2) 清缓存 / Zoom / Teams / 腾讯 / 定时任务
       @Order(3) 审批流流转
       @Order(4) 邮件 / 短信 / 通知 / 传感器
```

**关键认知**：新增一个会议副作用（如"预约成功后推送到某新平台"）**只需新增一个 Operator 类**，无需改事件类、无需改注册代码——Spring 事件广播 + `@Order` 编排。

#### 2.3.3 三层冲突检测（业务精华）

| 层          | 位置                                               | 职责                                                                                                                       |
| ---------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 第 1 层：前置校验 | `MeetingReserveCheckServiceImpl.preCheckMeeting` | 黑名单、会议名长度、用户/主持人会议室权限、代订限制、循环规则、访客规则、会议室状态（维护/停用）                                                                        |
| 第 2 层：时间占用 | `MakeMeetingServiceImpl.makeMeetingInfo`         | **核心**：查 `meeting_room` 表时间重叠（`end > start AND start < end`），含锁定时间缓冲（会议前后 N 分钟不排会）；冲突时组装 Tip 提示；审批管理员遇到"冲突的是待审批会议"可自动拒绝之 |
| 第 3 层：审批复检 | `MeetingAuditCheckServiceImpl.preCheckMeeting`   | **审批落定时再查一次冲突**（因为待审批会议不占用资源，审批期间时段可能被抢）                                                                                 |

#### 2.3.4 状态机（现状与问题）

**状态值**（`MeetingStatusEnum`，12 个）：`PENDING(0)` 未开始 / `OPENED(1)` 进行中 / `ENDED(2)` 已结束 / `CANCEL(3)` / `REJECT(4)` / `AUDIT(5)` 待审批 / `INVALID(6)` / `PROGRESS(7)` / `FAIL(8)` / `APPROVING(9)` / `CONFLICT(10)` / `DINGTALK_APPROVING(11)`

**迁移表**（`MeetingEventEnum`）：每个事件声明 `target`（目标状态）+ `src`（允许的来源状态），如 `RESERVE: → PENDING`、`AUDIT: AUDIT → PENDING`、`CANCEL: PENDING/REJECT → CANCEL`。

**⚠️ 问题**：状态机**双来源**（枚举值 + 事件枚举各管一半），且状态过多（12 个里一半是第三方同步专用）——新项目要收敛。

#### 2.3.5 审批流

- **判定路由**：会议室 `needAudit` 开关 + 循环会议审批策略 + 特殊预约组 → 决定预约是直接落库还是进 `AUDIT`
- **引擎**：完整 BPM（`BpmProcess`/`BpmFlow`/`BpmTask` 一族表），三类审批：会议 / 服务 / 设备
- **结果流转**：审批通过 → `AuditMeetingEvent`（`AUDIT → PENDING`，**且再次检冲突**）；拒绝 → `RejectMeetingEvent`（`AUDIT → REJECT` 终态）
- **超时处理**：`MeetingAuditOperator` + 定时任务（超时提醒/自动处理）

#### 2.3.6 事件引擎与 Operator（架构精华）

`meeting-core/process/` 下 **50 个 Operator** 监听同一 Spring 事件：`MeetingStatusChangeOperator`（状态机）、`MeetingBillingOperator`（计费 6787 行）、`MeetingZoomOperator`/`MeetingTeamsOperator` 等（12+ 平台对接）、`MeetingEmailOperator`/`MeetingSmsOperator`（通知）、`MeetingTaskOperator`（生成定时任务）、`MeetingInfraredCacheOperator`（传感器）。

**设计价值**：用"事件 + 多个独立操作者"解耦出一个会议操作的全部副作用，新增能力零侵入。

#### 2.3.7 其他企业能力（新项目按需取舍）

| 能力   | 原实现                                            | 取舍                |
| ---- | ---------------------------------------------- | ----------------- |
| 缓存   | 67 个类型化 Redis 缓存接口（每个业务域一个）                    | 保留简化              |
| 定时任务 | ITaskLoader（40）→ MQ 投递 → ITaskExecutor（42）异步执行 | 保留简化              |
| 提交流程 | 全链路注解 `@PreAuthorize` + 数据权限 `@IAuthority` 系列  | 保留简化              |
| MQ   | 双 MQ 抽象（Rabbit/Rocket 配置切换）+ MQTT              | 降为可进阶项            |
| 多租户  | TenantFilter + 字段级 AES 加密                      | ❌ 砍掉              |
| 日历同步 | Exchange/Google/钉钉/飞书双向同步                      | ❌ 砍掉              |
| 报表   | POI + EasyExcel + PPT 生成                       | ❌ 砍掉（简化成 2 个统计接口） |

#### 2.3.8 后端痛点（重构动机素材）

1. **上帝类**：`MeetingInfoServiceImpl` 11243 行、`RoomInfoServiceImpl` 8081 行、`MeetingBillingOperator` 6787 行
2. **状态双来源**：`MeetingStatusEnum` + `MeetingEventEnum` 交叉使用，改状态机要同时看两处
3. **死代码**：`@AuthCheck` 注解全项目零使用；流程引擎的"注册代码"是空实现
4. **Flyway 迁移没在跑**：配置 `enabled: false`，真实 SQL 靠发布流程手工执行

### 3.2 被选中的 8 条"好业务"（为什么它们值得保留）

1. **预约主链路的分阶段校验**——真实系统的预约从来不是"插一条记录"：权限、规则、资源、冲突要分层校验。这条链路是面试讲"业务→代码"的最佳素材。
2. **半开区间冲突检测**——`[start, end)` 的区间设计让"10:00-11:00 与 11:00-12:00 不冲突"成为自然结果。一个小设计体现工程功底。
3. **分布式锁防抢单**——"两个用户同时抢同一会议室"是面试官最爱追问的并发场景，Redisson 锁的粒度/超时/兜底有讲不完的细节。
4. **状态机**——从 12 个散乱状态收敛到 6 个清晰状态，本身就是"我做过重构"的叙事；状态迁移校验 + 定时补偿 + 幂等，每一个都是后端高频考点。
5. **审批通过复检冲突**——处理"审批期间资源被抢"的时序问题，展示对并发场景的深度思考（原系统最有价值的业务设计之一）。
6. **事件驱动解耦**——"预约成功后要做的 N 件事"从流水账代码变成发布-订阅。事务边界（AFTER_COMMIT）、同步 vs 异步、失败处理，全是可深挖点。
7. **定时任务驱动态**——为什么不懒加载？任务幂等怎么做？分批扫描防大事务？补偿机制如何兜底？
8. **缓存 + 限流**——Redis 三大问题（穿透/击穿/雪崩）在这个项目里有真实落地场景，而不是背诵八股。

### 3.3 砍掉清单（及理由）

**统一理由：面试讲不到 3 句话就说不下去的功能，不做。**

- 多租户/字段加密：复杂度 ×3，面试官一般不会追问到
- 第三方平台对接：全都依赖外部账号，无法本地演示
- 日历双向同步：涉及外部协议（EWS/Graph），跑不起来
- IoT/展板/屏幕：需要硬件
- 计费：规则复杂（原系统 6787 行）但无技术深度
- 报表导出：POI 写 Excel 是熟练度问题，不是设计问题
- 签到 / 回执 / 满意度评价：需要传感器或第三方配合才有"故事"，单独实现只是状态更新类 CRUD

## 四、新项目需求定义

### 4.1 项目定位与边界

**一句话**：一个会议室预约系统，核心解决"**并发预约下的时段冲突**"与"**会议状态生命周期的一致性**"两个工程问题。

**边界（明确不做）**：多租户、第三方会议平台、日历同步、IoT 设备、计费、报表导出、附件上传、国际化。

### 4.2 用户角色、权限与部门（RBAC 五表 + 部门树）

**数据模型**：标准 RBAC 五表——`sys_user`（用户）/ `sys_role`（角色）/ `sys_permission`（权限）
+ 关联表 `sys_user_role`（用户-角色）/ `sys_role_permission`（角色-权限）。

| 角色             | 说明          | 权限                               |
| -------------- | ----------- | -------------------------------- |
| `USER` 普通员工    | 日常使用者       | 浏览会议室、创建/修改/取消自己的预约、查看自己的会议和通知   |
| `APPROVER` 审批人 | 负责审批需审批的会议室 | USER 全部权限 + 审批操作（通过/拒绝）          |
| `ADMIN` 管理员    | 系统管理        | 全部权限 + 会议室 CRUD/策略配置、用户管理、查看全部会议 |

**多角色**：用户与角色为多对多（同一人可同时是 ADMIN 与 APPROVER），鉴权语义 = "拥有的任一角色满足即通过"。

**权限实现**：JWT 载荷携带 `roles` 数组 + 注解式角色校验（Spring Security `@PreAuthorize("hasRole(...)")`）；
`sys_permission` 表登记权限资源清单（接口 / 菜单 / 按钮），`sys_role_permission` 建立角色与资源的映射——
供前端菜单渲染与**后续升级为权限点鉴权**使用。**当前鉴权按角色判定，权限表暂不参与鉴权**
（避免 JWT 无状态与"权限变更即时生效"的一致性问题，属有意取舍）。
另有预约资源归属校验（只能操作自己的会议）。

**部门树**：`sys_dept`（`parent_id` 树形结构）+ `sys_user.dept_id`。
用途边界：**仅作组织结构**——部门用于组织用户、用户管理按部门筛选、选参会人时按部门浏览；
**不参与权限判定**（不做数据权限），也不影响会议室（会议室不挂部门）。

### 4.4 核心业务流程详述

#### 流程 1：创建预约（★最核心，含异常分支）

```
1. 接收请求（标题、会议室、开始/结束时间、参会人、备注）
2. 校验链（快速失败，逐层拦截）
   2.1 基础校验：时间合法性（start < end、非过去时间）、标题非空、会议室存在且可用
   2.2 策略校验：提前预约天数、单场时长 ≤ 会议室策略上限、预约窗口内
   2.3 权限校验：用户对该会议室是否有预约权限（可选：会议室可见范围）
3. 抢占分布式锁（key = lock:meeting:room:{roomId}:{yyyyMMdd}）
   —— 抢不到锁 → 返回"系统繁忙，请重试"（或短等重试一次）
4. 冲突检测（锁内执行，防止并发漏检）
   SQL 重叠判定：existing.start_time < newEnd AND existing.end_time > newStart
   有效状态：RESERVED / ONGOING（待审批不占用，见 4.6 规则 R-4）
   —— 冲突 → 返回冲突列表（冲突会议名、时间段、组织人），前端高亮提示
5. 落库（事务内）
   5.1 插入 meeting（状态：需审批 → PENDING_APPROVAL；否则 → RESERVED）
   5.2 插入参会人 meeting_participant
   5.3 需审批时插入/置待办（审批人维度）
6. 释放锁（finally）
7. 事务提交后发布事件（AFTER_COMMIT）
   → 通知监听者：通知申请人/参会人/审批人
   → 缓存监听者：清除该会议室该日的日历缓存
8. 返回结果（含会议 ID、状态、是否需审批）
```

**异常分支**：

| 分支            | 处理                                  |
| ------------- | ----------------------------------- |
| 锁等待超时         | 返回友好提示，不带"重试成功"的侥幸逻辑                |
| 冲突            | 返回冲突详情（哪场会议、时间段、组织人）                |
| 审批中会议被抢（时序问题） | 见流程 2：审批通过时复检                       |
| 重复提交（用户双击）    | 幂等保护：同用户 3 秒内相同参数请求 → 拒绝或返回已有结果（P1） |

#### 流程 2：审批（通过/拒绝）

```
审批人打开待审批列表 → 查看详情（申请人、时间、会议室、用途）
  ├─ 拒绝：记录原因 → 状态 REJECTED → 事件（通知申请人）
  └─ 通过：
       1. 【复检冲突】重新执行冲突检测（锁内）
          —— 等待期间时段已被占 → 审批通过失败，返回"时段已被占用"，通知申请人
       2. 状态 PENDING_APPROVAL → RESERVED
       3. 事件（通知申请人 + 参会人；清缓存）
```

> **面试点**：为什么待审批不占用时段？→ 权衡：占用会让"占坑不拉屎"堵死资源；不占用则需审批端复检兜底。选择后者 + 复检，并接受"审批可能失败"的业务后果。

#### 流程 3：取消与修改

```
取消：仅 RESERVED / PENDING_APPROVAL 可取消
  ├─ 权限：仅组织人（或 ADMIN）
  ├─ 策略：距开始时间不足"取消截止分钟数"时禁止取消（防临期放鸽子）
  └─ 状态 → CANCELLED → 事件（通知参会人 + 清缓存）

修改：仅 RESERVED 可改
  ├─ 改时间/会议室 → 完整走一遍校验链 + 锁 + 冲突检测（排除自身）+ 审批分流判定（R-14）
  └─ 改标题/备注/参会人 → 直接更新 + 通知新增参会人

延长（P1，ONGOING 状态的特例操作）：
  ├─ 计算上限：min(下一场会议开始 − 锁定缓冲, 当日 24:00)（R-15）
  ├─ 冲突检测（排除自身）→ 通过后更新 end_time
  └─ 发布事件（通知参会人）
```

#### 流程 4：生命周期自动流转（定时任务）

```
每分钟执行（扫描型任务，分批处理）：
  ① 开始任务：SELECT ... WHERE status = RESERVED AND start_time <= NOW() LIMIT 100
     → UPDATE status = ONGOING（逐批，每批一个事务）
  ② 结束任务：SELECT ... WHERE status IN (RESERVED, ONGOING) AND end_time <= NOW() LIMIT 100
     → UPDATE status = FINISHED
  （注：会议到点但无人签到的场景由 ①② 兜底处理——RESERVED 直接到 FINISHED）
```

**设计要点**：

- 任务幂等（重复执行不产生错误状态：靠状态条件约束 `WHERE status = X`）
- 分批扫描防大事务、防锁表
- 不用懒加载的原因：状态推进要触发副作用（通知、统计），懒加载不可靠

#### 流程 5：周期会议创建（P1）

```
输入：每周规则（每周X / 时间 / 时长 / 起止日期）
1. 展开为 N 个场次时间
2. 逐场冲突检测（锁保护）→ 收集冲突清单
   ├─ 任一冲突 → 整体失败，返回全部冲突场次（允许用户调整后重试）
   └─ 全部可用 → 批量创建（一个事务），写入 recurring_id
3. 单场修改/取消：操作"这一场"；系列取消：按 recurring_id 批量取消
```

### 4.5 状态机定义（收敛版）

**状态表**（6 个）：

| 状态                 | 值  | 说明            |
| ------------------ | -- | ------------- |
| `PENDING_APPROVAL` | 10 | 待审批（仅需审批的预约）  |
| `RESERVED`         | 20 | 已预约（终态前的主要状态） |
| `ONGOING`          | 30 | 进行中           |
| `FINISHED`         | 40 | 已结束（终态）       |
| `CANCELLED`        | 50 | 已取消（终态）       |
| `REJECTED`         | 60 | 已拒绝（终态）       |

**迁移表**（状态 × 事件）：

| 当前状态 \ 事件        | 创建(免审)     | 创建(需审)             | 审批通过       | 审批拒绝       | 开始时间到     | 结束时间到      | 取消          | 提前结束       | 修改（R-14：改到需审会议室） |
| ---------------- | ---------- | ------------------ | ---------- | ---------- | --------- | ---------- | ----------- | ---------- | ------------------ |
| （无）              | → RESERVED | → PENDING_APPROVAL | —          | —          | —         | —          | —           | —          | —                  |
| PENDING_APPROVAL | —          | —                  | → RESERVED | → REJECTED | —         | —          | → CANCELLED | —          | —（待审批不可改，R-12）     |
| RESERVED         | —          | —                  | —          | —          | → ONGOING | → FINISHED | → CANCELLED | —          | → PENDING_APPROVAL |
| ONGOING          | —          | —                  | —          | —          | —         | → FINISHED | —（禁止）       | → FINISHED | —（进行中不可改）          |

> 终态（FINISHED / CANCELLED / REJECTED）不出现在表中 = **没有任何出边**（R-11 不可逆）。
> "被拒后改期重送"的正确姿势是**重新提交一场新预约**，不是把 60 改回 10（2026-10-23 澄清，见 docs/05 T3.3）。
> 表中"修改"列由 T2.10 引入（原表漏画），2026-10-23 补登。

**实现要求**：

- 所有状态变更**必须经过状态机校验**（`StateMachine.transition(current, event)` → 新状态 or 抛异常），禁止业务代码直接 set 状态
- 每次变更记录操作日志（who/when/from/to/event）

### 4.6 关键业务规则清单

| 编号   | 规则      | 说明                                                                                                                   |
| ---- | ------- | -------------------------------------------------------------------------------------------------------------------- |
| R-1  | 时间格式与粒度 | 开始/结束时间为整分；演示用 15 分钟粒度（可选 30 分钟）                                                                                     |
| R-2  | 时间合法性   | `start < end`；单场时长 ≤ 会议室策略上限（如 4 小时）；不可预约过去时间                                                                        |
| R-3  | 半开区间判重  | 占用区间为 `[start, end)`；重叠条件：`existing.start < new.end AND existing.end > new.start`；相邻时段（11:00 结束 vs 11:00 开始）**不算冲突** |
| R-4  | 冲突判定状态  | 占用时段的状态：`RESERVED`、`ONGOING`；`PENDING_APPROVAL` **不占用**（审批通过时复检）                                                     |
| R-5  | 提前预约窗口  | 最多提前 N 天（会议室策略，默认 30 天）                                                                                              |
| R-6  | 取消截止    | 距开始不足 M 分钟（策略，默认 0/30 分钟）不可取消                                                                                        |
| R-7  | 审批路由    | 会议室 `need_approval = true` → 创建后进入 PENDING_APPROVAL                                                                  |
| R-8  | 锁粒度     | `lock:meeting:room:{roomId}:{date}`——同会议室同日互斥（粒度权衡：比"会议室"细、比"时段"简单可靠）                                                |
| R-9  | 限流规则    | 创建预约接口：同用户 5 次/分钟（P1）                                                                                                |
| R-10 | 缓存策略    | 会议室列表缓存 30 分钟；每日日历缓存 5 分钟；变更后主动删除（Cache-Aside + 延迟双删可选）                                                              |
| R-11 | 状态不可逆   | 终态（FINISHED/CANCELLED/REJECTED）不可再流转                                                                                 |
| R-12 | 修改约束    | 仅 RESERVED 可修改（延长除外，见 C-10）；改时间/房间等价于"取消+新建"的校验强度                                                                                 |
| R-13 | 会议室锁定缓冲（P1） | 可配置：会议开始前 / 结束后各留 N 分钟缓冲（默认关闭，开启建议 15 分钟；原系统 after_meeting_lock_time），缓冲区间同样参与判重 |
| R-14 | 修改后审批策略 | 修改"时间 / 会议室"后重新判定审批分流：目标会议室需审批 → 回到 PENDING_APPROVAL（原系统为多态返回值，新项目简化为两态） |
| R-15 | 延长上限 | 延长终点 ≤ min(下一场会议开始 − 锁定缓冲, 当日 24:00)；无下一场时延至营业结束 |

### 4.7 数据模型概览（15 张表）


## 五、面试叙事设计

### 5.1 项目讲述框架

**1 分钟版**（开场自我介绍时）：

> "我基于之前公司的会议室系统，独立重构了一个简化版：前后端分离，后端 Spring Boot + MySQL + Redis。它核心解决两个工程问题：一是**高并发下同一会议室时段预约的冲突控制**（Redisson 分布式锁 + 时间区间判重）；二是**会议状态生命周期的一致性**（状态机 + 定时任务补偿 + 事件驱动解耦）。从预约、审批到生命周期管理，整条链路我都能展开讲。"

**5 分钟版**（项目环节）：

1. 业务背景（30 秒）：会议室资源有限，预约有冲突风险、需审批场景、生命周期状态多
2. 技术架构（1 分钟）：分层、选型理由（为什么 Spring Boot / MyBatis-Plus / Redis）
3. 核心链路（2 分钟）：创建预约的校验链 → 锁 → 冲突检测 → 落库 → 事件
4. 一个深挖点（1.5 分钟）：挑状态机或分布式锁讲透（见 5.2）

**15 分钟版**：5 分钟版 + 三个深挖点（并发 / 状态机 / 事件驱动）+ 重构叙事（5.3）

### 5.2 面试深挖点与回答要点

**① 并发预约冲突怎么解决？**

- 锁粒度设计：`room + date`（为什么不是 room？—— 同会议室不同日期无冲突，锁太粗影响吞吐；为什么不是时间段？—— 边界难对齐、实现复杂）
- 锁细节：`tryLock` 带等待时间（用户体验）与租约（防死锁）；看门狗续期；`finally` 中 `isHeldByCurrentThread` 校验后释放
- 追问"Redis 挂了怎么办"：降级策略——数据库层兜底（唯一约束/事务 + 悲观锁兜底路径），或快速失败保数据正确性
- 追问"为什么锁了还要冲突检测"：锁只防并发时序，不判业务规则（半开区间、状态过滤）；两者职责不同

- 进阶叙事（原系统素材）：原系统还有第二重防护——Redis"预约中注册表"（记录未提交会议的可见性，随事务完成清理），用于周期会议批量入库期间的重复预约防护；新项目单场场景下"锁 + 事务"已足够，但理解这套设计意图

**② 时间冲突检测怎么实现？**

- 半开区间 `[start, end)` 与重叠条件 `existing.start < new.end AND existing.end > new.start`
- 为什么相邻不冲突：10:00-11:00 与 11:00-12:00 是合法排期，半开区间天然支持
- 索引设计：`(room_id, start_time, end_time)` 联合索引让检测走覆盖索引
- 边界：跨天会议（新项目不支持，讲清取舍）；精度（整分对齐）

**③ 状态机为什么这么设计？**

- 现状：6 状态 + 迁移表集中管理；对比原系统 12 状态双来源的坑（"改一个状态要翻两个枚举"）
- 所有流转过 `StateMachine.transition()`，非法迁移直接抛异常（防御式设计）
- 定时任务补偿：时间驱动的流转（开始/结束）不能依赖用户请求，扫描任务兜底
- 任务幂等：`WHERE status = 预期前态` 条件更新，重复执行无副作用

**④ 事件驱动解决什么问题？**

- 预约成功后要做 N 件事（通知申请人/参会人/审批人、清缓存、生成提醒任务）——如果全写在主流程里，方法膨胀且耦合
- 方案：事务提交后发布 `MeetingCreatedEvent`，多个监听者各管各的（通知/缓存/任务）
- 关键细节：`@TransactionalEventListener(phase = AFTER_COMMIT)`——避免"事务没提交就发通知，通知发出去但数据回滚了"的经典 bug
- 同步 vs 异步：通知类监听者 `@Async`（线程池隔离）；缓存清理同步做（要保证读一致性）
- 从原系统学到的：原系统用 50 个 Operator + @Order 编排解耦 12 个平台对接，我提炼了这个模式

**⑤ 审批与预约的时序问题？**

- 问题：待审批不占用时段 → 审批通过前时段可能被抢
- 两种策略对比：A "待审批即占用"（先到先得，但要处理超时释放、占坑堵塞）；B "不占用 + 审批时复检"（资源利用率高，但要处理审批失败）
- 我的选择：B + 复检机制，审批通过失败时明确通知申请人；这个设计直接来自原系统的真实业务

**⑥ 缓存怎么用？**

- 缓存对象：会议室列表（读多写少，30 分钟）、每日日历（5 分钟）
- 更新策略：Cache-Aside，变更后**先更新库、提交后删缓存**
- 三大问题：穿透（空值缓存/布隆过滤器）、击穿（互斥重建/逻辑过期）、雪崩（过期时间加随机）
- 讲清楚"为什么这个场景只需要删缓存不需要延迟双删"

- 防击穿的真实落地（原系统素材）：会议室缓存重建采用 single-flight——Redisson 互斥锁 + double-check + 异步回填，保证同一时刻只有一个线程回源重建；新项目照此思路做简化实现

**⑦ 限流怎么做的？**

- 场景：预约接口防刷（同一用户高频提交）
- 实现：Redis 计数器（`INCR + EXPIRE`）/ 滑动窗口（ZSET）；注解式（自定义 `@RateLimit` + AOP）
- 讲清"为什么在应用层限流"（网关限流 vs 应用层限流的适用场景）

- 固定窗口 vs 滑动窗口（重构叙事）：原系统用固定窗口计数器（INCR + EXPIRE），存在临界突刺（窗口边界两倍流量）；新项目直接用滑动窗口（ZSET）规避

**⑧ 周期会议的设计（如实现）？**

- 展开规则 → 逐场检测 → 全可用才创建（还是部分成功？——我选了"整体失败 + 返回冲突清单"，因为部分成功对用户心智负担大）
- 场次"关联但独立"：`recurring_id` 关联，单场可独立改/取消，系列取消按 id 批量

**⑨ 延长会议的核心设计？（如实现）**

- 延长是"修改结束时间"的特例：普通修改仅限 RESERVED，延长是 ONGOING 的例外（业务上"会没开完想续"）
- 上限的自然算法：`min(下一场会议开始 − 锁定缓冲, 当日 24:00) − 当前结束时间`——下一场会议是天然边界，无需人工设上限
- 延长后仍要冲突检测；原系统对第三方会议实现了"取消旧会议 + 新建"的另一套路径，新项目统一为"原地改 end_time"

### 5.3 "重构叙事"：为什么老系统这么设计，新项目为什么改

**这是最有说服力的一类回答——"我在真实系统里见过 X 问题"**：

| 老系统的问题                             | 我观察到          | 新项目怎么改                        |
| ---------------------------------- | ------------- | ----------------------------- |
| `MeetingInfoServiceImpl` 1.1 万行上帝类 | 预约/取消/同步全塞一个类 | 按领域拆 Service，主链路薄、副作用走事件      |
| 状态机双来源（枚举 + 事件表）                   | 改状态要同时翻两个地方   | 收敛为单一迁移表 + 统一 transition API  |
| 错误靠 msg 数字码（202364…）               | 前后端靠数字对暗号     | 统一错误码分层（HTTP 语义 + 业务码），msg 可读 |
| 定时任务靠 MQ 投递 + 42 个执行器              | 链路长、本地难调试     | 简化为扫描型任务，幂等 + 分批              |
| 预约冲突检测散在 3 个服务                     | 新人很难拼出全貌      | 收敛为"冲突检测服务"，一处维护              |
| 限流用固定窗口计数器（有临界突刺）               | 知道窗口边界会双倍放量    | 改用滑动窗口（ZSET）实现          |
| 事务后副作用手写 TransactionSynchronizationManager 散落各处 | 原理理解但写法繁琐      | 统一收敛为 @TransactionalEventListener 注解 |
| 缓存重建靠手写注册表 / 版本号 / 就绪标记组合        | 复杂度高、维护难       | 简化为 single-flight 互斥重建（够用就好） |
