### **T0.1 Docker 基础设施编排**
- **目标**：一个 compose 文件拉起 MySQL / Redis / RabbitMQ / Nacos 四件套
- **涉及文件（1）**：`deploy/docker-compose.infra.yml`（新）
- **实现内容**：① 4 个容器（mysql:8.0 / redis:7 / rabbitmq:3.13-management / nacos/nacos-server:v2.3.x）；② MySQL 挂载 `../db:/docker-entrypoint-initdb.d:ro`（首次启动自动建库+种子）；③ 端口 3306/6379/5672+15672/8848+9848，`TZ=Asia/Shanghai`；④ Nacos standalone 模式
- **验收标准**：☐ 4 容器全部运行；☐ MySQL 自动执行了 initdb 脚本；☐ Nacos 控制台可访问
- **验证**：`scripts/verify-m5-recurring.sh`（**30/30**，连跑两次均绿）。
- 📄 **契约已补登 docs/04 4.9**（原只有接口清单一行）：请求/响应、冲突清单形状、
  以及**新登记的错误码 40007**（该会议室未开放周期预约）。
- 🔍 **实现时定死的三点**：
  ① **系列 = "一批共享同一规则的普通会议"**（展开成 meeting 表里普通的一行 + recurring_id 回指）——
  状态机/冲突检测/改期/取消/审批/提醒**全都不用为周期会议写第二遍**，
  新增的只有"批量创建的原子性"与"系列级批量取消"；
  ② **锁住所有场次涉及的日期 → 再开事务**（锁 ⊇ 事务，红线 #8）：给 `MeetingLockHelper` 加了
  `executeWithLockOnDates`——只锁"真的要写的那几天"，而不是首末区间里的每一天
  （后者会无故阻塞别人的单场预约）；锁 key 与单场预约同一套 ⇒ 系列创建与并发单场预约互斥；
  ③ **缓存失效直接调用 evictor，不逐场发领域事件**：发 N 条事件 = N 条"预约创建"通知，
  组织人自己刚建的系列没必要收 5 条；缓存是本进程内的事，直接调用更直白（已在代码里写明理由）。
- ⚠️ **文档里那个示例区间是错的（已修）**：原写 `2026-10-19 ~ 2026-11-30`（42 天）**超过该会议室 30 天提前量**，
  会被校验链拒绝。逐场校验的语义是"每一场都要过与单场相同的校验链"，
  所以 endDate 的上限是"今天 + advance_days"——已把示例改成 ≤30 天并在 docs/04 4.9 写明规则。
- ⚠️ **写脚本时踩的两个坑**（都是"断言以错误的理由变红"）：
  ① 冲突场景复用了第 1 节刚建系列的**同一时段** → "占位"订不上、观察到的冲突其实是"自己跟自己的系列撞"
  （3 条而不是 1 条）→ 改用另一个窗口；
  ② 日历断言拿**跨三周的 3 个场次 id** 去核对**其中一周**的日历 → 永远"缺 2 个"→ 改为只核对该周那一场。
- **验证**：`scripts/verify-m5-recurring-cancel.sh`（**25/25**，连跑两次均绿）。
- 🔍 **实现时的三点**：
  ① **"仅未来场次"= 按状态过滤**（10/20 可取消；40/50/60 是历史，**跳过并计入 skipped**）。
  `skipped` 是有意返回给前端的：系列里往往已经有过去的场次，只回"取消了 4 场"会让人以为漏了；
  ② **进行中（30）→ 整个系列被拒**（40002 + 提示先单场处理）：把正在开的会"取消"在业务上说不通
  （它不是没发生，是正在发生）。⚠️ 这条**没法用数据构造**——校验链不允许创建过去的场次，
  所以验证脚本是造一场"1 分钟后开始"的会议、**真的等定时任务把它推成 30** 再验（约 2 分钟）；
  ③ **逐场走状态机 + 逐场发取消事件**（红线 #4）：每场一条 CANCEL 日志；事件逐场发是与单场取消保持一致，
  而系列场次通常没有参会人 → 实际不会产生通知；将来给某几场加了参会人，他们本来就该被告知。
- 📌 **连带补的索引**：`meeting.recurring_id` 此前**没有任何索引**，系列查询实测 `EXPLAIN type=ALL`（89 行小表也全扫）。
  已补 `idx_recurring (recurring_id, start_time)`（等值列 + 排序列），加后 `type=ref` + `Using index`（覆盖索引）。
  已同步 `db/01-schema.sql`、`docs/03` 5.5b 与索引表；**已建库需手动 ALTER**（文档里写了命令）。
- **验证**：`scripts/verify-m5-stats.sh`（**23/23**，连跑两次均绿）。
- 📄 **口径全部写死在 docs/04 4.10**（统计接口最容易出的不是 SQL 错，而是**口径各算各的**）：
  计入状态 20/30/40、时长按区间**裁剪**（`min(end,区间末) − max(start,区间初)`）、
  可用分钟 = 天数 × 720（08:00–20:00，**不给周末打折**——系统本就不禁止周末预约）、
  占用率是 **0~1 小数**、区间按**日期**解释且含端点。H-2 口径 = **我组织的 ∪ 我参与的**（与列表 `scope=mine` 一致；
  只算"我组织的"会让普通用户永远看到 0）。
- 🔍 **两个实现判断**：
  ① **聚合全部下推到 SQL**（group by + LEAST/GREATEST 裁剪）：这是数据库最擅长的事，
     拉到内存再分组等于把数据量问题留给应用；`LEFT JOIN meeting_room` 保证**零会议的会议室也出现**
     （否则前端柱状图会莫名少几根，看起来像"房间被删了"）；
  ② "我参与的"用 **EXISTS 子查询**而不是 JOIN：JOIN 会让"组织人同时是参会人"的场次出两行、COUNT 虚高。
- ⚠️ **踩到的一个 MyBatis 坑（已记 CLAUDE.md）**：显式 `resultMap` 是**按 setter** 映射的，
  所以**不可变 record 用不了**（`ReflectionException: There is no setter for property named 'roomId'`）；
  而 `resultType`（列别名 + 构造器路径）才能喂给 record。另外，让 mapper 去填一个 **SQL 里不存在的字段**
  （服务端算的 `usageRate`）会报 `IndexOutOfBoundsException: Index 4 out of bounds for length 4`——
  约定：**mapper 的返回类型只放 SQL 真查得到的东西**，派生值在 Service 里补。
- ⚠️ **写脚本时的两个"断言假设错"**（都与产品无关）：跨区间裁剪那节忘了同一会议室当天的另一场会（写成写死值→改差值）；
  H-2 的窗口是"**近** 30 天"（过去），而我拿**未来**会议当夹具 → 改用 SQL 造历史会议（40 已结束，本就是过去的会的真实状态）。

- ⚠️ **两类失败的行为不同，这是有意的**：结构非法（缺 msgId/data）**不重试**直接进死信
  （重试它也不会变好）；业务失败重试 3 次后进死信。两者都进 `meeting.dlq`（保留原 routingKey，能看出是哪个事件死的）。

- **目标**：网关生成 traceId → 全链路日志可串联

  ⚠️ 如实记录现状：**当前业务路径没有 Feign 调用**（T1.18/T1.19 建了内部接口与客户端，但查询都靠同库 JOIN），

- **验收对照**：☑ 一次请求的日志在 2+ 服务中 traceId 一致（网关 + meeting-service，同一 id 两侧各有日志）；
  ☑ 无头请求不报错（经网关→网关生成；**直连业务服务**→服务自己生成，日志不留空、也不打 `traceId:null`）。

- 🔍 **实现时定死的四点**：
  ① **切面顺序在事务之外**（`@Order(HIGHEST_PRECEDENCE + 10)` 包住 `@Transactional`）：耗时含事务，

- ⚠️ **自调用失效（笔记 11 章的坑）**：只标注"被 Controller 从外部调用"的公开方法

  审计日志的意义就是只追加、不可删改（脚本里写明了这条，免得后人"顺手清理"把审计清了）。

### **T5.5 后端容器化（Dockerfile ×4 + 全量 compose）**

## 九、风险与调整预案

| 风险 | 征兆 | 预案 |
|------|------|------|
| **时间不足（最可能）** | M2 未按期完成 | 按"面试价值"砍：先砍 M5 周期会议 → 再砍 M4.7 缓存 → 再砍 T5.4 看板。**绝不砍**：T2.6 锁 / T3.2 复检 / T4.3 幂等（面试核心） |
| Spring Cloud Alibaba 版本兼容卡壳 | 启动报 Bean 定义冲突 | 回退组合：SB 3.2.5 + SC 2023.0.3 + SCA 2023.0.1.2（官方对应表为准）；Nacos Server 保持 2.3.x |
| 网关 + WS 联调困难 | 升级请求 404 | 优先直连 notification-service 演示（:8083），网关联调降级为加分项 |
| 前端进度拖后 | 占用后端时间 | 前端降级：只保留 T1.F1-F3 + T2.F1/F2（登录/日历/预约），其余用 Postman/curl 演示；**后端优先原则** |
| 延迟消息队头阻塞坑 | 提醒不准时 | 已规避（固定 15 分钟单一延迟）；如仍异常→降级为 T3.5 扫描任务加提醒逻辑（两方案本就可切换） |
| 本机环境问题（MySQL 未跑等） | M0 卡住 | 以 Docker 为准（T0.1）；确保 Docker Desktop 内存 ≥ 6G（Nacos+RabbitMQ 吃内存） |

**开发节奏建议**：
- 每个任务一个 vibe coding 会话：先让 AI 读对应文档章节（如 T2.6 → 读 02 文档 5.2 + 03 文档 4.1），再实现，再跑验证命令；
- 任务完成即 commit（`feat(T2.6): Redisson 锁防并发`）；
- 每完成一个里程碑，把"演示脚本"跑一遍（既能发现集成问题，也是面试彩排）。
