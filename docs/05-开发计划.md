- **验收标准**：☐ refresh 换新 token 成功、旧 refresh 失效（20003）；☐ logout 后 refresh 返回 20003；☐ me 不带 token 直连 8081 返回 401（服务侧也应校验）——备注：服务侧校验可选（信任网关），此处直连测试放宽

- **实现内容**：① 找 `status=20 AND start_time < now-2h` / `status IN (20,30) AND end_time < now-2h` 的异常记录；② 修状态 + 打 ERROR 日志（告警线索）；③ 记录补偿次数（日志）

- 🔍 **实现时的发现（重要，别当成"兜底很扎实"）**：上面这两个时间条件（过了 2 小时）
  其实是正常轮询条件（`<= NOW()`）的**子集**——正常轮询每分钟一次，永远先修完。
  所以对 20/30 而言，这条"兜底"只在**正常任务自己停摆**的时间窗内才有意义，而那种情况下

  否则永远看不到对账在工作（两条路径都在改同一批数据，先到先得）。
- 🔍 **补了一类真正会永久卡住的数据**：`status=10` 且时间已过的待审批会议——

### **T4.1 meeting-service：MQ 接入与事件发布**（✅ 已完成，2026-10-16）
- **目标**：预约/审批/取消三个时点发事件消息（topic exchange）

- **验收标准**：☐ 创建预约后 RabbitMQ 控制台可见消息；☐ 事务回滚时不发消息（afterCommit 验证）
- **验证命令**：创建一场会议 → 打开 http://localhost:15672 → Queues 观察 `meeting.created` 消息
- **验证**：`MeetingEventPublisherTest`（2 例，"提交才发/回滚不发"）+ `scripts/verify-m4-mq.sh`（16/16：五类事件真投到 broker，
  核对 routingKey 与 payload，自清理）。⚠️ "回滚不发"这条**走 HTTP 造不出来**——失败点发生在业务代码最后一步之后，
  只有把 `RabbitTemplate` mock 掉、在事务里手动抛异常才测得到。
- 🔍 **实现时的三个判断**（都不是文档原话，写下来免得被当成"随手写的"）：
  ① **消息不带参会人快照**——参会人可改，快照会把通知发给错的人；"自包含"的正解是"**不回调生产服务**"（消费端可查库），不是"消息里必须什么都有"。
  ② Publisher 的 `@TransactionalEventListener(fallbackExecution = true)` **必须配 try/catch**：AFTER_COMMIT 阶段抛出的异常会冒泡回调用方，
  于是"数据已提交 + 前端收到 500"——这正是 M3 里 `insertLog` 那类问题的手足（用户看到失败会重试，重试又会撞幂等）。
  ③ **启动即声明拓扑**（`ApplicationRunner` 调 `AmqpAdmin.initialize()`）：Spring AMQP 生产端是**懒连接**，不主动连的话队列要等第一次发消息才被创建，
  而 topic exchange 路由不到任何队列 = **静默丢弃**（不报错、不重试）。实测：只声明不初始化时，管理台里一个队列都没有。
- ⚠️ 两个坑：Boot 自动配置里的 `RabbitAdmin` bean **声明类型是 `AmqpAdmin`**（按实现类注入匹配不上 → 启动直接失败）；
  管理台 API 的 `messages` 统计**有 ~5 秒缓存**，刚发完就查显示 0，看起来像"消息没发出去"（验证脚本因此改用 `/api/queues/{q}/get` 实时取）。

## 九、风险与调整预案

| 风险 | 征兆 | 预案 |
|------|------|------|
| **时间不足（最可能）** | M2 未按期完成 | 按"面试价值"砍：先砍 M5 周期会议 → 再砍 M4.7 缓存 → 再砍 T5.4 看板。**绝不砍**：T2.6 锁 / T3.2 复检 / T4.3 幂等（面试核心） |
| Spring Cloud Alibaba 版本兼容卡壳 | 启动报 Bean 定义冲突 | 回退组合：SB 3.2.5 + SC 2023.0.3 + SCA 2023.0.1.2（官方对应表为准）；Nacos Server 保持 2.3.x |
| 网关 + WS 联调困难 | 升级请求 404 | 优先直连 notification-service 演示（:8083），网关联调降级为加分项 |
| 前端进度拖后 | 占用后端时间 | 前端降级：只保留 T1.F1-F3 + T2.F1/F2（登录/日历/预约），其余用 Postman/curl 演示；**后端优先原则** |
| 延迟消息队头阻塞坑 | 提醒不准时 | 已规避（固定 15 分钟单一延迟）；如仍异常→降级为 T3.5 扫描任务加提醒逻辑（两方案本就可切换） |
| 本机环境问题（MySQL 未跑等） | M0 卡住 | 以 Docker 为准（T0.1）；确保 Docker Desktop 内存 ≥ 6G（Nacos+RabbitMQ 吃内存） |

**开发节奏建议**：
- 每个任务一个 vibe coding 会话：先让 AI 读对应文档章节（如 T2.6 → 读 02 文档 5.2 + 03 文档 4.1），再实现，再跑验证命令；
- 任务完成即 commit（`feat(T2.6): Redisson 锁防并发`）；
- 每完成一个里程碑，把"演示脚本"跑一遍（既能发现集成问题，也是面试彩排）。
