## 一、设计约定

| 约定项 | 选择 | 理由 |
|--------|------|------|
| 库名 | `smt_meeting`（单库） | 延续原系统命名；单库决策见 02 文档 2.4（按表归属逻辑划分：auth 表 / 会议表 / 通知表） |
| 字符集/排序 | `utf8mb4` / `utf8mb4_0900_ai_ci` | MySQL 8 默认；完整支持中文与 emoji |
| 引擎 | InnoDB | 事务 + 行锁是我们并发设计的依托 |
| 主键 | `BIGINT` 自增 | 避免 INT 溢出；不用 UUID（自增有序，B+ 树写入友好；分布式扩展时再谈雪花） |
| 时间类型 | `DATETIME`（**不用 TIMESTAMP**） | 无 2038 问题；不绑定数据库时区（时区交给应用层 `LocalDateTime`） |
| 状态值 | `TINYINT` 数字（10/20/30…） | 与状态机约定一致；留 gap（10 步长）便于插值扩展 |
| 枚举字符串 | 角色/事件/类型用 `VARCHAR` | `ADMIN` 比 `3` 可读、调试友好；与 Spring Security `hasRole('ADMIN')` 直接对齐 ★（TINYINT 与 VARCHAR 的混搭理由见第五章） |
| 外键 | **不建外键约束** | 理由见第五章（面试高频追问） |
| 逻辑删除 | **不用 del_flag** | 会议室/用户用 `status` 停用；会议用 `status=50 取消`；净数据量小、无恢复诉求 ★ |
| 审计字段 | 全表 `created_at` + `updated_at`（`ON UPDATE CURRENT_TIMESTAMP`） | 排查与审计底线 |

## 二、ER 总览

```plaintext
【权限与组织】（RBAC 五表 + 部门树，见 3.1.1）
  sys_dept ──▶ sys_user ──▶ sys_user_role ──▶ sys_role ──▶ sys_role_permission ──▶ sys_permission
  （部门树）    （挂 dept_id）（用户角色关联）   （角色）     （角色权限关联）        （权限清单）

【业务】
                    ┌────────────┐
                    │  sys_user  │ 用户
                    └──────┬─────┘
        organiser_id ┌─────┴─────┐ user_id (participant) / user_id (notification)
                     ▼           ▼
┌────────────┐  ┌─────────┐  ┌──────────────────┐   ┌──────────────┐
│ room_group │─▶│meeting_room│ │ meeting_participant│   │ notification │
└────────────┘  └────┬────┘  └──────────────────┘   └──────────────┘
                     │ 1:1            ▲
                     ▼                │ meeting_id
              ┌─────────────┐  ┌──────┴──────┐   ┌──────────────────┐
              │room_strategy│  │   meeting   │──▶│ meeting_approval │（1:N，审批历史）
              └─────────────┘  └──────┬──────┘   └──────────────────┘
                                      │ recurring_id（自关联系列，P1）
                                      ├──▶ ┌───────────────────┐
                                      │    │ meeting_recurring │
                                      │    └───────────────────┘
                                      └──▶ ┌─────────────────────┐
                                           │ meeting_status_log  │（1:N，状态流转审计）
                                           └─────────────────────┘
```

**关系要点**：
- `sys_user` ↔ `sys_role` 是 **N:N**（`sys_user_role`），`sys_role` ↔ `sys_permission` 是 **N:N**（`sys_role_permission`）
- `sys_dept` 自关联树（`parent_id`），`sys_user.dept_id` 指向部门（可为空 = 未分配）
- `meeting_room` ↔ `room_strategy` 是 **1:1**（每间会议室一份策略，`uk_room` 约束）
- `meeting` ↔ `meeting_participant` / `meeting_approval` / `meeting_status_log` 都是 **1:N**
- `meeting.recurring_id` 指向 `meeting_recurring.id`（非空表示属于某个周期系列）
- 所有关联关系**由应用层维护**（无外键约束）

## 三、表结构详解

> 完整 DDL 见 `db/01-schema.sql`（含每列 COMMENT）。本节给设计意图与关键字段解释。

### 3.1 sys_user 用户表

| 字段 | 类型 | 说明 |
|------|------|------|
| username | VARCHAR(50) | 登录名，`uk_username` 唯一 |
| password | VARCHAR(100) | **BCrypt 哈希**（60 字符，留余量；绝不存明文） |
| real_name | VARCHAR(50) | 姓名（展示/通知用） |
| email | VARCHAR(100) | 邮箱（通知用） |
| dept_id | BIGINT | 所属部门（`sys_dept.id`，可空 = 未分配）★ v1.3 新增 |
| status | TINYINT | 0 禁用 / 1 启用（**停用代替删除**，历史会议的组织人始终可查） |

**设计说明**：角色**不再用 `sys_user.role` 单字段**，升级为 RBAC 五表（见 3.1.1）——
原单角色设计表达不了"ADMIN 兼 APPROVER"；升级后鉴权语义为"任一角色满足即通过"，
`sys_permission` 资源清单还可支撑前端菜单渲染与后续权限点鉴权扩展。

### 3.1.1 RBAC 五表 + 部门树（v1.3 新增）

**sys_role 角色表**

| 字段 | 类型 | 说明 |
|------|------|------|
| code | VARCHAR(30) | `USER` / `APPROVER` / `ADMIN`，`uk_code` 唯一（**鉴权按 code**） |
| name | VARCHAR(50) | 显示名（普通用户 / 审批人 / 管理员） |
| description | VARCHAR(200) | 描述 |
| status | TINYINT | 1 启用 / 0 停用 |

**sys_permission 权限表**（资源清单：当前**不参与鉴权**，供前端菜单与后续扩展预留）

| 字段 | 类型 | 说明 |
|------|------|------|
| code | VARCHAR(50) | 权限标识（如 `room:manage`），`uk_code` 唯一 |
| name | VARCHAR(50) | 显示名 |
| type | TINYINT | 1 菜单 / 2 按钮 / 3 接口 |
| sort_order | INT | 排序 |

**sys_user_role 用户角色关联**（N:N 中间表）

| 字段 | 类型 | 说明 |
|------|------|------|
| user_id | BIGINT | 联合唯一 `uk_user_role(user_id, role_id)` 防重复授权 |
| role_id | BIGINT | — |

**sys_role_permission 角色权限关联**（N:N 中间表）

| 字段 | 类型 | 说明 |
|------|------|------|
| role_id | BIGINT | 联合唯一 `uk_role_permission(role_id, permission_id)` |
| permission_id | BIGINT | — |

**sys_dept 部门表**（树形；用途仅"组织结构"——组织用户与筛选，不参与权限判定）

| 字段 | 类型 | 说明 |
|------|------|------|
| parent_id | BIGINT | 父部门（0 = 根），`idx_parent` 支撑树查询 |
| name | VARCHAR(50) | 部门名 |
| sort_order | INT | 同级排序 |
| status | TINYINT | 1 启用 / 0 停用 |

**设计说明**：三块职责——`sys_user_role` 决定"你是谁"（可多角色），`sys_role_permission` 决定"你的角色能碰哪些资源"，
`sys_permission` 是资源字典。**当前鉴权只用角色**（JWT 携带 roles 数组），权限表作清单备用——
这是有意取舍：避免 JWT 无状态与"权限变更即时生效"的一致性问题（面试考点）。

### 3.2 room_group · 3.3 meeting_room

**room_group**：只做一层分组（如"3F 东区"），不做无限级树——需求场景两层足够，树形留给"区域→楼层→房间"确实需要的系统。

**meeting_room 关键字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| group_id | BIGINT | 所属分组，`idx_group` |
| capacity | INT | 容量（前端筛选排序用） |
| images | JSON | 图片 URL 数组（腾讯云 COS 地址） |
| device_tags | JSON | 设备标签数组，如 `["投影仪","视频会议"]` |
| status | TINYINT | 0 可用 / 1 维护中（维护中不可预约，对应原系统 checkRoomStatus） |

**★ JSON 字段的取舍**（面试点）：`images`/`device_tags` 用 JSON 而非关联表——因为它们是**只读展示属性**（不需要按设备反查会议室）。如果哪天要"查所有带投影仪的会议室"，MySQL 8 也支持 `JSON_CONTAINS(device_tags, '"投影仪"')`；再进一步才考虑拆关联表。**决策逻辑：查询模式决定存储结构**。

### 3.4 room_strategy 预约策略（1:1）

| 字段 | 类型 | 默认 | 说明 |
|------|------|------|------|
| need_approval | TINYINT | 0 | 0 免审 / 1 需审批（R-7 审批路由） |
| advance_days | INT | 30 | 最多提前预约天数（R-5） |
| max_duration_minutes | INT | 240 | 单场时长上限（R-2） |
| cancel_deadline_minutes | INT | 0 | 取消截止（R-6） |
| buffer_minutes | INT | 0 | **锁定缓冲**（R-13，会议前后各 N 分钟不排会） |
| allow_recurring | TINYINT | 1 | 是否允许周期会议 |

**设计说明**：策略独立成表而非塞进 `meeting_room`——因为策略字段多、变动频率与基础信息不同（改策略不该动会议室主数据）；1:1 用 `uk_room` 保证。

### 3.5 meeting 会议主表（★核心）

| 字段 | 类型 | 说明 |
|------|------|------|
| room_id / organiser_id | BIGINT | 会议室 / 组织人 |
| start_time / end_time | DATETIME | **占用区间为半开区间 `[start, end)`**（R-3） |
| status | TINYINT | 10 待审批 / 20 已预约 / 30 进行中 / 40 已结束 / 50 已取消 / 60 已拒绝 |
| cancel_reason / cancel_time | — | 取消原因与时间（01 文档 C-4） |
| recurring_id | BIGINT NULL | 周期系列 ID（P1） |
| version | INT | **乐观锁版本号**（修改会议时 `WHERE version=?`） |

**状态设计**：数字值与 01 文档状态机完全对齐；**终态（40/50/60）不可再流转**由应用层状态机保证（数据库不做 CHECK 约束——约束逻辑放应用层，便于演进）。

### 3.6 meeting_participant 参会人（N:N 中间表）

- 结构：`meeting_id` + `user_id`（均 NOT NULL）——**标准多对多中间表**：一场会议多个参会人、一人可参加多场会议
- **联合唯一键 `uk_meeting_user(meeting_id, user_id)`**：防重复参会人（中间表标配）；
  其最左前缀已覆盖"按会议查参会人"的检索，故不再单建 `idx_meeting`
- 反向索引 `idx_user(user_id)`：支撑"我参加了哪些会议"的反向查询
- **v1.3 变更**：移除外部参会人字段（`is_external` / `external_name` / `external_email`）——参会人只能是系统用户；
  原"访客邀约"能力整体砍掉（01 文档功能对照第 12 项），如未来需要应以独立"外部联系人"表重建，而非同表混存

### 3.7 meeting_approval 审批记录（⚠️ 一对多）

**为什么不加唯一约束**：审批记录是**动作历史**——会议被拒 → 修改 → 重新送审 → 再次审批，同一 `meeting_id` 会有多条记录。单级审批的"唯一性"体现在：**同一时刻只有一条待处理记录**，这在业务上通过"会议状态 + 行锁"保证，而非表约束。（对比 02 文档初稿里"meeting_id 唯一"的写法——这里修正为历史表语义 ★）

### 3.8 notification 站内通知

| 字段 | 说明 |
|------|------|
| type | `MEETING_CREATED` / `APPROVAL_TODO` / `APPROVAL_RESULT` / `MEETING_REMIND` / `MEETING_UPDATED` / `MEETING_CANCELLED` |
| meeting_id | 可空（点击通知跳转会议详情用） |
| read_flag | 0 未读 / 1 已读 |

**索引 `idx_user_read (user_id, read_flag, created_at)`**：支撑"我的未读列表按时间倒序"这个最高频查询。

### 3.9 meeting_recurring 周期规则（P1）

| 字段 | 类型 | 说明 |
|------|------|------|
| day_of_week | TINYINT | 1=周一 … 7=周日（**每周重复**，01 文档 F-1） |
| start_minutes | INT | 当天第几分钟（如 540 = 09:00）★ |
| duration_minutes | INT | 时长 |
| start_date / end_date | DATE | 重复区间 |

**★ 为什么用 `start_minutes` 而不是 TIME**：周期展开时的计算（"每周三的 540 分钟"）用整数直接做 `LocalDate + 分钟` 运算，避免 TIME/DATETIME 的时区与格式转换开销；存的是"规则参数"而不是"某个具体时间点"——**语义更准确**。

### 3.10 meeting_status_log 状态变更日志

- 对应状态机要求："每次变更记录 who/when/from/to/event"
- `operator_id` 可空（定时任务/系统触发的流转没有操作人）
- 写入时机：状态机 `transition()` 成功后同事务插入（不靠业务代码自觉）

## 四、索引设计与验证

### 4.1 冲突检测（核心查询）★

**业务 SQL**（含 R-3 半开区间 + R-13 锁定缓冲扩展区间）：

```sql
-- 预约前冲突检测：检测 [newStart, newEnd) 与已有会议是否重叠
-- 开启锁定缓冲时，把检测区间扩展为 [newStart - buffer, newEnd + buffer)
SELECT m.id, m.title, m.start_time, m.end_time, m.organiser_id, m.status
FROM meeting m
WHERE m.room_id = ?                                   -- ① 等值
  AND m.status IN (20, 30)                            -- ② 占用时段的状态
  AND m.start_time < ?                                -- ③ newEnd（半开区间：< 而非 <=）
  AND m.end_time   > ?                                -- ④ newStart（半开区间：> 而非 >=）
  AND m.id <> ?;                                      -- ⑤ 修改场景排除自身
```

**索引** `idx_room_time (room_id, start_time, end_time)` 的配合逻辑：

| 条件 | 用索引的方式 |
|------|-------------|
| `room_id = ?` | 联合索引第 1 列，**等值定位** |
| `start_time < ?` | 第 2 列，**范围扫描**（最左前缀原则：等值列后接范围列） |
| 其余条件 | 索引第 3 列 `end_time` 可继续过滤（避免回表后过滤）；`status`/`id` 走回表过滤 |

**EXPLAIN 预期（自测清单）**：

| 列 | 预期值 | 说明 |
|----|--------|------|
| type | `range` | room_id 等值 + start_time 范围 |
| key | `idx_room_time` | 命中目标索引 |
| rows | 个位数~几十 | 单会议室窗口内会议数很少 |
| Extra | `Using index condition`（理想）| ⚠️ 若出现 `Using filesort`/`Using temporary` 说明写法有问题，回查 SQL |

> ⚠️ 为什么不把 `status` 放进联合索引（如 `(room_id, status, start_time)`）：`status IN (20,30)` 是低基数多值条件，放在范围列前面会导致索引无法连续利用；当前写法让"高选择性 + 范围"两列充分发挥。**面试时这是"最左前缀 + 选择性"的活教材**。

### 4.2 其他查询与索引对照

| 查询场景 | SQL 特征 | 命中索引 |
|---------|---------|---------|
| 定时任务·开始流转 | `WHERE status=20 AND start_time<=NOW()` | `idx_status_start (status, start_time)` |
| 定时任务·结束流转 | `WHERE status IN (20,30) AND end_time<=NOW()` | `idx_status_end (status, end_time)` |
| 待审批列表（T3.1） | `WHERE status=10 ORDER BY start_time` | `idx_status_start` 复用（等值前缀 + 有序，无 filesort） |
| 审批中心·已处理（T3.1） | `WHERE approver_id=? ORDER BY created_at DESC` | `idx_approver_time (approver_id, created_at)`【2026-10-15 新增，见下】 |
| 我的会议列表 | `WHERE organiser_id=? ORDER BY start_time` | `idx_organiser (organiser_id, start_time)` |
| 周期系列查询（T5.2） | `WHERE recurring_id=? [AND start_time>?] ORDER BY start_time` | `idx_recurring (recurring_id, start_time)`【2026-10-16 新增，见下】 |
| 未读通知 | `WHERE user_id=? AND read_flag=0 ORDER BY created_at DESC` | `idx_user_read (user_id, read_flag, created_at)` |
| 消息消费幂等 | （Redis SETNX，不落库） | — |

> **`idx_approver_time` 的来由（T3.1 实现时实测）**：`meeting_approval` 原先只有 `idx_meeting`，
> 而审批中心的"已处理"列表按 `approver_id` 过滤 + 按时间倒序 —— 实测 EXPLAIN 是 **`ALL` + `Using filesort`**
> （全表扫描）。补上 `(approver_id, created_at)` 后该查询走索引且天然有序。
> ⚠️ **已建好的库需要手动执行一次**（`01-schema.sql` 只在数据卷首次初始化时跑）：
> `ALTER TABLE meeting_approval ADD INDEX idx_approver_time (approver_id, created_at);`
>
> **`idx_recurring` 的来由（T5.2 实现时实测）**：`meeting.recurring_id` 此前**没有任何索引**，
> 而系列取消/展开校验都按它过滤。实测 EXPLAIN 是 **`type=ALL`**（89 行的小表也已全表扫），
> 加上 `(recurring_id, start_time)` 后变成 `type=ref`，`ORDER BY start_time` 不必 filesort。
> ⚠️ **不是覆盖索引**：只有 `SELECT recurring_id, start_time` 这类窄查询才是 `Using index`；
> 实际 `selectByRecurringId` 选全部列，EXPLAIN 的 Extra 为 NULL（仍回表）。
> 列序是"等值列 + 排序列"；当前 SQL 没有 `AND start_time > ?` 过滤，未来若加可直接走索引区间。
> ⚠️ **已建好的库同样需要手动执行一次**：
> `ALTER TABLE meeting ADD INDEX idx_recurring (recurring_id, start_time);`
>
> 另有两处 EXPLAIN 实测与"理想"有出入，如实记录（数据量小时无害，量级上来要回看）：
> ① 定时任务·结束流转带 `ORDER BY end_time` 时，因 `status IN (20,30)` 是多值范围，
> 计划里出现 `Using index; Using filesort`（仍走索引取数，只是额外排了"已到期"那一小撮）；
> ② "下一场会议"查询（`room_id=? AND status IN (20,30) AND start_time>=?`）的索引选择**随数据分布摆动**：
> 同一台库上 `room_id=1` 时优化器选 `idx_status_start`、`room_id=5` 时选 `idx_room_time`（都是成本决策，
> 当前数据量下谁也压不倒谁）。这不影响正确性，但**别把它当成"稳定命中某条索引"写进结论**——
> 量级上来后按房间过滤的 `idx_room_time` 才是更合适的那条。

### 4.3 索引设计小结（面试表述模板）

> "这个系统的索引全部围绕**访问路径**设计：写入路径（预约）靠 `idx_room_time` 扛冲突检测；后台任务路径靠 `idx_status_start/end` 扛扫描；用户路径靠 `idx_organiser` 扛列表。每条索引都能说清楚'为哪条 SQL 服务、EXPLAIN 预期是什么'——没有'反正建上'的索引。"

## 五、关键设计决策（面试深挖点）

### 5.1 ★ 为什么不建外键约束？

| 角度 | 说明 |
|------|------|
| 性能 | 外键校验是行锁级别的开销（插入参会人时校验会议/用户存在性），高并发写入受牵连 |
| 架构 | 微服务趋势下"数据归属单一服务"，跨服务无法建外键；单库练习也保持一致习惯 |
| 一致性 | **一致性由应用层保证**：事务 + 业务校验（如插入参会人前先校验会议存在）+ 定时对账 |
| 代价意识 | 不建外键 = 把校验责任拿回应用层，必须有意识地补上（面试要主动说出这个代价，而不是只说"不用"） |

### 5.2 ★ 为什么不用逻辑删除（del_flag）？

- 会议室/用户："删除"的真实诉求是**停用**（历史会议要能查到会议室名、组织人名）→ 用 `status` 表达，语义更准；
- 会议：有独立的"取消"状态（业务概念），不需要额外的删除态；
- 数据量级：单表远未到需要"软删保留"的量级，物理删除（仅限误建数据）成本可控；
- **结论**：先想清楚"删除的业务含义"，再决定要不要技术手段——很多系统 del_flag 泛滥，是没想清语义。

### 5.3 ★ 区间重叠检测：为什么唯一约束兜底不成立？

- 直觉方案："给 meeting 加个 `(room_id, 时间段)` 唯一约束"——**做不到**：SQL 唯一约束只能表达"值相等"，**无法表达"区间相交"**；
- 真正的数据库层兜底 = **行锁**：事务内先 `SELECT id FROM meeting_room WHERE id=? FOR UPDATE`（锁住会议室行）→ 再查冲突 → 再写入。并发请求在会议室行上排队，效果等价于"串行化同一会议室的预约"；
- 最终架构：**Redis 分布式锁（第一道，性能好）+ 数据库行锁（兜底/降级路径，正确性最后防线）**；
- ⚠️ 注意：`FOR UPDATE` 必须在事务里、且 `WHERE` 走索引（命中 `meeting_room` 主键），否则锁范围会失控——正好是"行锁加在索引上"（笔记 12 章）的实战场。
- ★ **适用范围（T2.10 踩坑后补）**：这条兜底不是"创建预约专用"，而是**所有改变"某时段是否被占用"的写路径都要取这把行锁**——创建（T2.4）、改期（T2.10）、审批通过（T3.2，把 10 待审变 20 占用）。少一条路径，那条路径就是双保险的缺口；
- ★ **锁序**：若一个事务需要同时锁会议室行与会议行（审批场景），一律**先会议室行 → 后会议行**，全项目统一顺序，避免交叉持锁死锁。

### 5.4 状态用 TINYINT、角色用 VARCHAR，为什么不统一？

| 维度 | 状态（TINYINT） | 角色/类型（VARCHAR） |
|------|---------------|---------------------|
| 变更频率 | 状态机枚举稳定（写死在代码常量） | 枚举可能扩充（新增通知类型） |
| 使用方式 | 数值比较、排序、gap 扩展（10/20/30） | 直接与代码字符串（`ADMIN`）对应、调试可读 |
| 业务语义 | "阶段"适合数字化 | "身份/种类"适合命名化 |
| 结论 | 不是"必须统一"，而是**按语义选型**——能说清取舍就是好设计（面试常见陷阱题：两个都行，看你怎么讲） |

> **v1.3 变更**：角色已从 `sys_user.role` 单字段升级为 RBAC 五表（见 3.1.1）。
> 本节的"角色用 VARCHAR"原则**沿用到了 `sys_role.code`（VARCHAR(30)）**——身份标识仍是可读字符串，
> 只是从用户表挪进了角色表；状态仍为 TINYINT。取舍逻辑不变。

### 5.5 乐观锁 version 用在哪（会/不会用在哪）？

- **用**：修改会议（改时间/标题）——并发冲突低概率但要防"两人同时编辑互相覆盖"，`UPDATE ... SET version=version+1 WHERE id=? AND version=?`，影响行数 0 → 提示"会议已被修改，请刷新"；
- **不用**：预约主链路（高并发场景用行锁/分布式锁而非乐观锁重试——重试风暴）；审批（用行锁保证只处理一次）；
- **面试表述**："乐观锁适合低冲突场景（编辑类），悲观锁/分布式锁适合高竞争场景（抢占类）"。

### 5.6 审批记录表为什么允许"一对多"？

见 3.7——审批是**历史动作**（拒绝后改期重审会产生多条）；"同一时刻只能有一条待办"由状态机 + 行锁保证。**表结构反映业务的历史性，约束表达不了业务时序**——约束归应用层。

### 5.7 ★ 单库表归属（面向未来分库的"预埋"）

单库不等于没有边界——三组表天然归属未来的三个服务：

| 归属 | 表 | 未来的库 |
|------|-----|---------|
| auth-service | sys_user | `smt_auth` |
| meeting-service | room_group / meeting_room / room_strategy / meeting / meeting_participant / meeting_approval / meeting_recurring / meeting_status_log | `smt_meeting` |
| notification-service | notification | `smt_notify` |

**关键点**：三组之间**没有跨组事务**（通知是异步最终一致）——这就是"生产环境可以原地分库而不用上分布式事务"的原因 ★（能回答"你现在单库，将来怎么拆"）。

### 6.3 为什么种子数据不预置"会议"？
