## 〇、5 分钟速览

**一句话**：把「订会议室」这件小事，重做成一个**微服务 + 前后端分离**的系统，用真实工程问题练手。

**这个项目真正在练什么**（比"做了个会议室系统"重要得多）：

| # | 核心工程问题 | 什么时候做 | 为什么值钱 |
|---|-------------|-----------|-----------|
| 1 | **并发预约下的时段冲突控制** | M2 | 两个人同时订同一间会议室同一时段，怎么保证只有一个成功？（分布式锁 + 区间判重） |
| 2 | **会议状态生命周期的一致性** | M3 | 会议到期该自动结束、审批该流转、通知该发出——状态机 + 定时补偿 + 事件驱动 |

**M0/M1 做的事，本质是给这两个问题搭舞台**：把基础设施、认证、会议室管理这些"地基"先立稳，M2 才开始动真格。

**代码规模**（可直接跑）：

```

         ├── gateway           3 个类（:8080 网关）
         ├── auth-service     29 个类（:8081 认证 + RBAC/部门）
         └── meeting-service  42 个类（:8082 会议核心；T2.x 进行中）
web/     React 18 + TS strict        └── 16 个文件（:5173 前端）
```

## 二、M0 做了什么：地基（3 个任务）

> 对应 `docs/05-开发计划.md` 的 T0.1~T0.3。**这一阶段没写业务代码，但它决定了后面所有代码的运行环境。**

### 2.1 T0.1 Docker 四件套 → `deploy/docker-compose.infra.yml`

一个 compose 文件拉起 4 个容器，**为什么要这四个**：

| 组件 | 在后端扮演什么角色 | ≈ 前端类比 |
|------|------------------|-----------|
| **MySQL 8.0** | 持久化业务数据（10 张表） | 你调接口时数据的最终来源（≈ 后端的"真值"） |
| **Redis 7** | 存 refreshToken 双索引（登录态） | ≈ localStorage 的服务端版，但**可主动失效**（登出即删） |
| **RabbitMQ 3.13** | M4 通知的异步消息队列 | ≈ 事件总线（EventEmitter），但跨进程、可持久化 |
| **Nacos 2.4** | 服务注册发现（谁在哪个 IP 哪个端口） | ≈ 前端的模块解析/import map，服务之间靠"名字"找对方 |

**关键设计**：MySQL 挂载了 `../db:/docker-entrypoint-initdb.d:ro` —— **首次启动自动建库 + 灌种子数据**。这就是为什么你 `docker compose up` 之后直接就有 6 个用户 6 间会议室。（踩坑记录见第六节 #1）

**看代码**：`deploy/docker-compose.infra.yml`（很短，5 分钟能读完，重点看 MySQL 的 volumes 挂载和 TZ 时区设置）

### 2.2 T0.2 数据库 10 张表 → `db/01-schema.sql` + `db/02-seed.sql`

**M1 用到的 4 张表**（其余 6 张属于 M2/M3/M4）：

```
sys_user       用户（admin/user1...，密码是 BCrypt 密文）
room_group     会议室分组（3F 东区/西区/4F 区）
meeting_room   会议室（青竹厅/白桦厅...，images/device_tags 是 JSON 列）
room_strategy  预约策略（1:1 于会议室：是否需审批/提前天数/时长上限/缓冲...）
```

**5 条设计约定**（`01-schema.sql` 头部注释写了，值得读）：

1. 主键统一 `BIGINT` 自增；时间用 `DATETIME`（不用 TIMESTAMP → 避开 2038 和时区坑）
2. 状态用 `TINYINT` 数字（会议状态 10/20/30...）；角色 code 用 `VARCHAR` 但**不再存于用户表**——v1.3 起走 RBAC 五表（`sys_user_role` 关联，一人可多角色）
3. **不用外键约束**（关系由应用层维护——为什么？见 `docs/03` 第五章，是面试点）
4. **不用逻辑删除**（会议室用 `status` 停用，会议用 `status=取消`）
5. 所有表带 `created_at / updated_at`

**注意 `meeting_room` 的 JSON 列**：`images` 和 `device_tags` 存的是 JSON 数组字符串。这直接决定了后端要用自定义 `TypeHandler` 来读写（见第五节 #6）。

> **v1.3 数据模型变更（2026-10-15）**：表从 10 张扩到 **15 张**——新增 RBAC 五表（`sys_role`/`sys_permission` + 两张关联表）
> 与 `sys_dept` 部门树；`sys_user` 删 `role` 列改挂 `dept_id`；`meeting_participant` 回归标准 N:N 中间表
> （删外部参会人字段 + 补联合唯一键）。详见 `docs/03` 的 3.1.1 节。

## 三、M1 做了什么：骨架 + 认证 + 会议室（23 任务）

> 后端 19 个任务（T1.1~T1.19）+ 前端 4 个任务（T1.F1~T1.F4）。按 M1 的**实现顺序**讲，因为这顺序本身就是设计思路。

### 3.1 后端的搭建顺序（为什么是这个顺序）

```
T1.1~T1.5  meeting-common     先立"共享地基"：统一响应/异常/JWT工具/用户上下文
T1.6~T1.7  gateway            再立"大门"：路由 + JWT 验签 + 身份注入
T1.8~T1.12 auth-service       然后"谁能进来"：登录/双token/用户管理
T1.13~T1.16 meeting-service   最后"进来干什么"：会议室数据层→查询→管理
T1.17~T1.19 收尾               接口文档(springdoc) + 内部接口 + Feign 调用
```

**底层逻辑**：认证是业务的前置条件 → 先把"进门"的事做完，业务才有意义。前端则是"最后才做"，因为**前端要调的接口必须先存在**。

### 3.2 meeting-common：为什么单独抽一个模块

`server/meeting-common/src/main/java/com/smt/common/`，10 个类：

| 文件 | 职责 | 你会关心的问题 |
|------|------|--------------|
| `result/Result.java` | 统一响应 `{code,msg,data}` | 为什么不是 HTTP 状态码表达一切？→ 看 `docs/04` 1.3，**HTTP 管传输/认证，code 管业务** |
| `result/ErrorCode.java` | 29 个错误码枚举（分段 1xxxx~6xxxx） | 前端拦截器靠它分支处理 |
| `exception/GlobalExceptionHandler.java` | 全局异常 → 统一响应 | **重点**：框架异常不能被兜底误伤（第五节 #3） |
| `util/JwtUtil.java` | JWT 签发/解析（jjwt 0.12 新 API） | 0.12 的 API 和老教程完全不同，别按记忆写 |
| `context/UserContext.java` | ThreadLocal 存当前用户 | ≈ 前端的 React Context，但**是线程私有的** |
| `context/LoginUser.java` | 用户信息 record | record ≈ TS 的 `Readonly<{...}>` 不可变对象 |
| `filter/UserHeaderFilter.java` | 读网关注入的头 → 恢复用户上下文 | **重点**：为什么它必须挂在 Security 链内（第五节 #2） |
| `config/CommonWebAutoConfiguration.java` | 自动配置（各服务引入即生效） | Spring 的"约定优于配置"（第五节 #4） |
| `result/PageResult.java` | 分页响应 `{list,total,page,size}` | — |
| `exception/BusinessException.java` | 业务异常（携带 errorCode） | 业务代码只管抛，怎么响应交给全局处理器 |

**关键机制：自动配置（≈ 前端库的 side-effect import）**

`meeting-common` 不是被 auth/meeting 服务"手动 new"的，而是通过 `META-INF/spring/...AutoConfiguration.imports` 声明：**"引入我这个 jar，我就自动帮你装好异常处理、JWT、用户上下文"**。这就是为什么 auth-service 和 meeting-service 的启动类里看不到任何异常处理相关的配置——它们是被自动装配的。

> 前端类比：≈ `import 'antd/dist/reset.css'` 这种"引入即生效"的副作用导入，只不过 Spring 用的是 SPI 文件而非 import 语句。

### 3.3 gateway：大门（T1.6~T1.7）

**就三个类**，但价值极高：

| 文件 | 职责 |
|------|------|
| `GatewayApplication.java` | 启动类（注意：它 exclude 了 7 个 Security 自动配置，原因见第六节 #5） |
| `filter/JwtAuthFilter.java` | **全局过滤器**：剥离伪造头 → 白名单放行 → 验签 → 注入身份头 |
| `config/AuthProperties.java` | 绑定配置（JWT 密钥、白名单列表 `@ConfigurationProperties`） |

**路由配置**（`gateway/src/main/resources/application.yml`）：

```yaml
routes:                          # /api/auth/login → 转发到 auth-service 的 /auth/login
  - Path=/api/auth/**,/api/users/**     → lb://auth-service      (StripPrefix=1 去掉 /api)
  - Path=/api/rooms/**,/api/meetings/** → lb://meeting-service
  - Path=/api/notifications/**          → lb://notification-service
```

`lb://` 就是"从 Nacos 找到服务实例再转发"——**这就是微服务里服务间调用的样子**，不需要硬编码 IP。

### 3.4 auth-service：认证（T1.8~T1.12）

```
controller/AuthController.java      login / refresh / logout / me
controller/UserController.java      用户搜索 / 分页 / 创建 / 启停  （/users/**）
controller/InternalUserController.java 服务间接口（/internal/**，网关不可达）
service/AuthService.java            登录校验 + 双 token 签发 + 滚动刷新
service/UserService.java            用户业务（搜索/分页/创建）
store/RefreshTokenStore.java        Redis 双索引 + **Lua 原子轮换**（第五节 #7）
mapper/SysUserMapper.java + resources/mapper/SysUserMapper.xml   手写 SQL
entity/SysUser.java  dto/*.java  vo/*.java   三层数据对象
```

**三层数据对象的分工**（这是后端很常见的模式，值得理解）：

| 类型 | 是什么 | ≈ 前端类比 |
|------|--------|-----------|
| `entity/` | 数据库表的映射（字段和表列一一对应） | 直接用后端返回的结构 |
| `dto/` | 入参（含校验注解 `@NotBlank` 等） | 表单的类型定义（≈ zod schema） |
| `vo/` | 出参（**对外只暴露该给的字段**） | 接口响应类型 |

**为什么分三层**：`SysUser` entity 里有 `password` 字段，但 `LoginResponse.User`（vo）里没有——**出参永远不带密码**，这是安全底线（评审已核实全项目 vo 零密码泄露）。

### 3.5 meeting-service：会议室（T1.13~T1.19）

```
controller/RoomController.java       会议室 CRUD（管理操作 @PreAuthorize("hasRole('ADMIN')")）
controller/RoomGroupController.java  分组查询
service/RoomService.java             业务逻辑（创建时连带建默认策略）
mapper/*.java + resources/mapper/*.xml   手写 SQL（本节重点）
entity/MeetingRoom.java  RoomGroup.java  RoomStrategy.java
handler/JsonTypeHandler.java         JSON 列 ↔ List<String> 互转（第五节 #6）

**`RoomService.create()` 的一个细节**（值得看）：创建会议室时**顺带创建默认策略**，两件事在同一个 `@Transactional` 里——要么都成功，要么都回滚。这就是"事务"的直观意义：≈ 前端的 `Promise.all`（要么都完成），但后端的事务是**数据库层面的原子承诺**。

## 四、四条核心链路走读（最重要，照着走一遍）

> 这一节是"把代码串起来"的部分。建议打开对应文件，跟着箭头读。

### 链路 1️⃣：一次登录，代码走了哪些地方

```
① 浏览器          POST /api/auth/login {username, password}
② Vite 代理       5173 → 8080（vite.config.ts 的 proxy）
③ gateway         JwtAuthFilter：/api/auth/login 在白名单 → 直接放行
④ gateway 路由    StripPrefix 去掉 /api → 转发到 lb://auth-service 的 /auth/login
⑤ AuthController  @Valid 校验入参（LoginRequest）
⑥ AuthService     selectByUsername 查库（SysUserMapper.xml）
                  → passwordEncoder.matches(明文, BCrypt密文)
                  → 失败统一 20001（防枚举：不区分"用户不存在"和"密码错"）
                  → 成功：jwtUtil.generate() 签 accessToken + UUID 生成 refreshToken
                  → refreshTokenStore.save() 写 Redis 双索引
⑦ 响应            {code:0, data:{accessToken, refreshToken, expiresIn, user:{...}}}
⑧ 前端            userStore.login() → 存 localStorage + navigate 跳转
```

**要看的关键代码**：
- `gateway/.../JwtAuthFilter.java` 的 `isWhitelisted()`（白名单判断）
- `auth-service/.../AuthService.java` 的 `login()`（三步：查人 → 验密 → 发 token）
- `auth-service/src/main/resources/mapper/SysUserMapper.xml`（手写 SQL）

### 链路 2️⃣：带 token 的请求，鉴权发生在哪

```
① 浏览器          GET /api/rooms（请求头带 Authorization: Bearer eyJ...）
② gateway JwtAuthFilter：
   a. 先剥离请求里可能伪造的 X-User-Id / X-User-Roles    ← 关键安全设计！
   b. 不在白名单 → 取 Bearer token → jwtUtil.parse() 验签+验过期
   c. 验签通过 → 解析出 userId/roles 数组 → **重新注入** X-User-Id / X-User-Roles（逗号分隔）
③ 转发到 meeting-service
④ UserHeaderFilter（服务内）：
   a. 读 X-User-Id / X-User-Roles → UserContext.set(LoginUser)  ← ThreadLocal
   b. 同时桥接 SecurityContext（ROLE_ADMIN 权限对象）
   c. finally 里 clear（防线程复用串数据）
⑤ RoomController.list()：
   无 @PreAuthorize（全员可查）→ 直接执行
   RoomController.create() 有 @PreAuthorize("hasRole('ADMIN')") → 校验不通过抛 403
```

**为什么"先剥离再注入"是精髓**：信任边界只在网关。就算攻击者直接给网关发一个 `X-User-Id: 1` 的头，也会被剥掉；只有网关验签后**自己重新写上**的身份头才作数。（评审复核确认：大小写变体、多值头都被正确剥离，无可绕过点。）

### 链路 3️⃣：accessToken 过期了，前端怎么"无感刷新"

```
多个并发请求都带了已过期的 accessToken
        ↓ 网关全部返回 401
request.ts 响应拦截器捕获第一个 401
        ↓
refreshPromise 为 null → 发起 POST /auth/refresh（用 refreshToken）
        ↓                            ← 后面到达的 401 请求发现 refreshPromise 已存在，
        ↓                              直接 await 同一个 Promise（不重复发请求！）
刷新成功 → setTokens 更新 localStorage + refreshToken（滚动更新）
        ↓
用新 token 重放原请求（instance(config)），用户完全无感知
```

**这就是 single-flight**（`web/src/api/request.ts`）。E2E 实测：篡改 token 后 3 个并发请求 → `/auth/refresh` **只发了 1 次**。

### 链路 4️⃣：会议室管理闭环（M1 验收）

```
admin 登录 → 侧边栏「管理端 → 会议室管理」
  → 列表：useAppRequest(listRooms) 拉取 → 表格渲染（含分组/状态筛选）
  → 新增：Modal + RHF + zod 校验 → POST /api/rooms → 刷新列表

## 五、核心难点代码精讲（8 个）

> 每个都给出**文件路径 + 为什么 + 代码怎么读**。建议打开文件对照。

### #1 网关 JWT 过滤器：顺序即安全

📁 `server/gateway/src/main/java/com/smt/gateway/filter/JwtAuthFilter.java`

```java
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    // ① 剥离外部伪造的身份头（无论是否白名单，统一先剥）
    ServerHttpRequest stripped = request.mutate()
            .headers(headers -> {
                headers.remove(HEADER_USER_ID);
                headers.remove(HEADER_USER_ROLE);
            }).build();

    // ② 白名单放行
    if (isWhitelisted(path)) return chain.filter(...stripped...);

    // ③ 验签 → 注入（只有这里写进去的头才可信）
    Claims claims = jwtUtil.parse(token);
    builder.header(HEADER_USER_ID, String.valueOf(jwtUtil.getUserId(claims)));
    ...
}
```

**三个要点**：
1. **先剥离、后注入**：顺序不能反，否则攻击者的头会活下来
2. 白名单路径也要剥离（登录接口同样不该带身份头进来）
3. 失败统一 `401 + {code:10002}`——**前端只认 HTTP 401 触发刷新**（业务错误都是 200 + code，见 `docs/04` 1.3）

**注意 `getOrder()` 返回 -100**：`GlobalFilter` 靠 order 决定执行顺序，越小越先执行。≈ 前端中间件的优先级。

### #2 身份桥接过滤器：为什么必须挂在 Security 链内部

📁 `server/meeting-common/.../filter/UserHeaderFilter.java` + `config/CommonWebAutoConfiguration.java`

```java
protected void doFilterInternal(...) {
    try {
        resolveIdentity(request);        // 读头 → UserContext.set + SecurityContext 桥接
        filterChain.doFilter(request, response);
    } finally {
        UserContext.clear();             // ★ 必须清，否则线程池复用会"串数据"
        SecurityContextHolder.clearContext();
    }
}
```

```java
// CommonWebAutoConfiguration 里的关键一行：
.addFilterAfter(userHeaderFilter, SecurityContextHolderFilter.class);
```

**为什么是 `addFilterAfter` 而不是随便注册**：Spring Security 的 `SecurityContextHolderFilter` 会在**每次请求开始时重置上下文**。如果你的身份过滤器挂在它**之前**，刚 set 进去的身份马上会被重置掉——表现为"明明带了头，但 @PreAuthorize 一直 403"。这个坑当初调试了很久，注释里写明了。

**`finally` 里的 clear 是后端独有的思维**：Tomcat 用**线程池**处理请求，同一个线程会服务不同用户。ThreadLocal 不清 → **下一个用户的请求可能读到上一个用户的身份**（≈ 前端模块级变量在 SSR 场景的串数据问题）。

### #3 全局异常处理：框架异常不能被兜底误伤

📁 `server/meeting-common/.../exception/GlobalExceptionHandler.java`

六个处理器，**按"谁更具体谁先生效"设计**：

```java
BusinessException          → HTTP 200 + 业务 code（业务错误不改 HTTP 状态）
MethodArgumentNotValidException → 200 + 10001（@Valid 校验失败，附具体字段）
NoResourceFoundException   → 404 + 10004（★ 不加这个会被下面的 Exception 兜底成 500）
AccessDeniedException      → 403 + 10003（★ 同上，@PreAuthorize 失败必须 403 不是 500）
AuthenticationException    → 401 + 10002
Exception（兜底）           → 500 + 10000（不向客户端暴露堆栈）
```

**核心认知**：`@ExceptionHandler(Exception.class)` 是"兜底"，但 Spring 自己的框架异常（404/405/参数类型错）也继承自 Exception——**如果你不显式接住它们，它们就会被兜底吞成 500**。这是当初真实踩的坑（当时访问不存在的路径返回 500 而不是 404）。

> ⚠️ 评审遗留：目前还有 `HttpMessageNotReadableException`（请求体 JSON 格式错）等少数框架异常未显式接住，仍在 500 兜底里。已记录在 `docs/review-M1.md` P1-11，第 4 批修复。

### #4 自动配置：common 怎么"引入即生效"

📁 `server/meeting-common/.../config/CommonWebAutoConfiguration.java`

```java
@AutoConfiguration
@ConditionalOnWebApplication(type = SERVLET)   // ★ 只对 Servlet 应用生效
@EnableMethodSecurity                           // 打开 @PreAuthorize
@Import(GlobalExceptionHandler.class)
public class CommonWebAutoConfiguration {
    @Bean SecurityFilterChain permissiveSecurityFilterChain(...) {
        http.csrf(disable)                     // 无状态 API 不需要 CSRF
            .authorizeHttpRequests(anyRequest().permitAll())  // ★ 服务内全放行
            .addFilterAfter(userHeaderFilter, SecurityContextHolderFilter.class);
    }
}
```

**两个设计要点**：

1. **`anyRequest().permitAll()` 不是"没做鉴权"**：鉴权由**网关**（JWT）+ **方法级注解**（@PreAuthorize）两层承担。服务内的 Security 只负责"提供方法级鉴权的机制"，不负责拦截请求。
   ⚠️ 代价：任何**忘记写 `@PreAuthorize`** 的写操作方法就是全开放的（已列入评审 P2，建议 CI 扫描）。
2. **`@ConditionalOnWebApplication(type = SERVLET)`**：gateway 是 WebFlux（响应式）应用，这个配置对它是**自动跳过**的——所以 gateway 不会意外获得 Servlet 的异常处理器。

### #5 手写 MyBatis XML：为什么不用 MyBatis-Plus 的便利

📁 `server/meeting-service/src/main/resources/mapper/MeetingRoomMapper.xml`

这是**刻意的练习选择**（你的要求：多练 SQL）。看四个关键写法：

```xml
<!-- ① 显式 resultMap：列名 → 属性名 一一对应（下划线转驼峰也不偷懒） -->
<resultMap id="BaseResultMap" type="com.smt.meeting.entity.MeetingRoom">
    <id column="id" property="id"/>
    <result column="group_id" property="groupId"/>
    <result column="images" property="images"
            typeHandler="com.smt.meeting.handler.JsonTypeHandler"/>   <!-- ② JSON 列特殊处理 -->
</resultMap>

<!-- ③ <sql> 片段复用列清单 -->
<sql id="BaseColumns">id, name, group_id, ...</sql>
<select id="selectById" resultMap="BaseResultMap">
    SELECT <include refid="BaseColumns"/> FROM meeting_room WHERE id = #{id}
</select>

<!-- ④ 动态 SQL：<where> 自动处理 AND 前缀——比手拼字符串安全优雅 -->
<select id="selectList" resultMap="RoomVOMap">
    SELECT ... FROM meeting_room r
    LEFT JOIN room_group g ON g.id = r.group_id        <!-- 联查直出 VO，避免 N+1 -->
    <where>
        <if test="groupId != null">AND r.group_id = #{groupId}</if>
        <if test="capacity != null">AND r.capacity &gt;= #{capacity}</if>
        <if test="status != null">AND r.status = #{status}</if>
    </where>
</select>
```

**三个必须记住的安全/性能点**：
1. **`#{}` vs `${}`**：`#{}` 是预编译参数（防 SQL 注入），`${}` 是字符串拼接（危险）。全项目**零 `${}` 滥用**（评审核实）。
2. **分页手写**：`LIMIT #{offset}, #{size}` + 独立 `COUNT(*)` 查询，不用插件。
3. **联查直出 VO**：列表要"会议室 + 分组名 + 策略"，一次 LEFT JOIN 拿全——**避免 N+1**（1 次查列表 + N 次查分组名）。≈ 前端避免"列表里每个 item 再发一次请求"。

**看代码**：`SysUserMapper.xml` 里的 `<foreach>`（`IN (?,?,?)` 批量查询，T1.18 的教学点）。

### #6 自定义 TypeHandler：让 JSON 列"看起来像普通字段"

📁 `server/meeting-service/.../handler/JsonTypeHandler.java`

**问题**：DB 的 `images` 列存的是 JSON 字符串 `'["a.jpg","b.jpg"]'`，但 Java 实体里想要 `List<String>`。

**解决**：写一个 `BaseTypeHandler<List<String>>`，MyBatis 读写这两个列时自动转换：

```java
// 写：Java List → JSON 字符串
setNonNullParameter(...) → objectMapper.writeValueAsString(parameter)
// 读：JSON 字符串 → Java List（带边界处理）
getNullableResult(...) → 空值返回 List.of()，脏数据抛异常（不静默吞）
```

**为什么不用 MyBatis-Plus 的 JacksonTypeHandler**：练习目的，且自定义版本能定制"空值返回空列表 vs 抛异常"的策略。在 XML 里通过 `typeHandler="..."` 属性挂载（见 #5 的 ②）。

### #7 双 token + Lua 原子轮换（今天的 P0 修复）

📁 `server/auth-service/.../store/RefreshTokenStore.java` + `service/AuthService.java`

**设计**：Redis 存双索引

```
auth:refresh:{userId}        → refreshToken    （按用户管理：登出/踢下线）
auth:refresh:token:{token}   → userId          （按 token 反查：刷新时用）
```

**为什么两个索引**：刷新接口只拿到 token，需要反查 userId；登出只知道 userId，需要找到 token 来删。两个方向都要快。

**难点：滚动更新的原子性**。原来是这样写的（有 bug）：

```java
// ❌ 多步非原子：并发时会互相破坏
String oldToken = redis.get(userKey);      // 两个并发请求都读到旧值
if (oldToken != null) redis.delete(tokenKey(oldToken));
redis.set(userKey, newToken, ttl);         // 后写者覆盖
redis.set(tokenKey(newToken), userId, ttl);
```

**并发下的后果**：两个请求都通过校验 → A 写入新 tokenA → B 覆盖成 tokenB 且删掉 tokenA 的反向索引 → **A 拿到的 tokenA 立刻失效**（用户被迫重登）+ 残留脏索引。

**修复：整段塞进 Lua 脚本，Redis 单线程保证原子执行**：

```java
private static final RedisScript<String> ROTATE_SCRIPT = new DefaultRedisScript<>("""
        local uid = redis.call('GET', KEYS[1])          -- 反查 userId
        if not uid then return nil end
        local ukey = ARGV[4] .. uid
        local current = redis.call('GET', ukey)
        if current ~= ARGV[1] then return nil end      -- 校验旧 token
        redis.call('DEL', KEYS[1])                     -- 删旧反向索引
        redis.call('SET', ukey, ARGV[2], 'PX', ARGV[3])-- 写新用户索引
        redis.call('SET', KEYS[2], uid, 'PX', ARGV[3]) -- 写新反向索引
        return uid
        """, String.class);
```

**效果**：校验+轮换在 Redis 内部一气呵成，并发请求只有一个能成功。**验证过**：并发两个 refresh → 一个 code 0、一个 20003。

> `px` 是毫秒 TTL；`KEYS`/`ARGV` 是 Lua 脚本的约定入参（KEYS 是键名，ARGV 是普通参数）。

### #8 Feign：微服务之间怎么互相调用

📁 `server/meeting-service/.../feign/AuthFeignClient.java` + `AuthFeignFallbackFactory.java`

**场景**：meeting-service 要显示参会人姓名，需要调 auth-service 查用户。**不想手写 HTTP 客户端**（拼 URL/序列化/反序列化太繁琐）。

```java
@FeignClient(name = "auth-service",                    // ★ 用服务名，不是 IP！
             fallbackFactory = AuthFeignFallbackFactory.class)
public interface AuthFeignClient {
    @PostMapping("/internal/users/batch")              // ★ 内部路径（网关不可达）
    Result<List<UserBriefVO>> batchUsers(@RequestBody UserBatchDTO dto);
}
```

**Feign 的本质**：声明一个接口 + 注解，Spring 帮你生成实现类（≈ 前端把 `axios.get` 封装成 `api.getUser()`）。`name = "auth-service"` 会去 Nacos 查实例地址，所以**不写死 IP**。

**降级（fallback）**：auth-service 挂了怎么办？

```java
public AuthFeignClient create(Throwable cause) {
    return dto -> {
        log.warn("[Fallback] auth-service 调用失败，降级返回空结果: {}", cause.getMessage());
        return Result.success(List.of());     // 不抛异常，返回空
    };
}
```

**降级策略的选择**（`docs/02` 3.1 #4）：认证域故障**不应该阻断预约主流程**——查不到姓名就显示 id，比整个预约接口 500 要好。

**两个必须掌握的配置坑**：
1. `spring.cloud.openfeign.circuitbreaker.enabled: true` —— **不打开这个，`fallbackFactory` 不生效**（降级永远不会触发，直接抛异常）
2. 需要 `spring-cloud-starter-loadbalancer` 依赖，否则报 "No servers available"

> ⚠️ 评审遗留（P1-16）：Feign 目前没配超时（默认 read 60 秒）——auth 卡顿时会拖慢调用线程。第 2 批修复。

## 六、今天踩过的 10 个坑（这些比顺利的过程值钱）

> 全部真实发生、已解决。**面试时讲"我踩过什么坑"比讲"我用了什么技术"更能证明你真做过。**

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | initdb 后中文全是乱码 | 容器内 mysql 客户端默认字符集不是 utf8mb4，中文按 latin1 解释（双重编码） | SQL 头加 `SET NAMES utf8mb4` |
| 2 | 服务启动端口诡异（不是配置的端口） | 环境变量 `SERVER__PORT` 劫持了 `server.port` | 启动命令加 `env -u SERVER__PORT` |
| 3 | 访问不存在的路径返回 500 | 框架的 `NoResourceFoundException` 被 `Exception` 兜底吞了 | 显式加 404/403/401 处理器 |
| 4 | 服务发现失效：所有接口超时 | 机器休眠后本机 IP 从 `192.168.18.20` 变成 `192.168.0.100`，但服务在 Nacos 注册的还是旧 IP | `nacos.discovery.ip: 127.0.0.1`（本地回环注册，不随网卡变） |
| 5 | 经网关的 POST 全部 403 | gateway 是 WebFlux 但经 common 拿到了 security-core，触发了默认安全链的 CSRF 防护；GET 被 JwtAuthFilter 抢先返回 401 掩盖了问题 | 启动类 exclude 7 个 Security 自动配置（含 actuator 的，漏了会启动失败） |
| 6 | Feign 降级"验证通过"了，其实是假的 | Nacos 里根本没注册 auth 实例（`No servers available`），503 触发了降级——但这不是"真降级"的证明 | 先确保实例注册成功再测降级 |
| 7 | pnpm 装不了 node_modules | 本机文件系统代理层下 pnpm 的 symlink 农场随机 ENOENT/EEXIST | 改用 npm（`.npmrc` 有记录） |
| 8 | vite dev 崩溃 | 依赖预构建要删旧缓存目录（58 文件）被批量删除保护拦截 | `mv` 移走残留缓存（rename 不触发保护） |
| 9 | 并发刷新后 token 秒失效 | refreshToken 滚动更新是"读→删→写"多步非原子 | Redis Lua 脚本原子化（第五节 #7） |
| 10 | 登录失败控制台一堆 Uncaught (in promise) | RHF 的 `handleSubmit` 内部重抛 reject，而调用处没 catch | 表单提交加 try/catch 收敛（错误已由 useAppRequest toast） |

**这些坑的共性**：大多是**"看着正常但实际不对"**（401 掩盖 403、假降级、GET 掩盖 POST）。排查方法：**别信"看起来通了"，要验证"预期的那条路径真的走了"**。
