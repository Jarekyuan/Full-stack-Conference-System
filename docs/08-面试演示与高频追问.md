## 二、开场（1 分 30 秒）

### 2.1 一句话版本

> 这是一个会议室预约系统，业务闭环是“预约 → 审批 → 进行中 → 结束/取消”，
> 技术上是 Spring Cloud 微服务 + React 18；我重点解决两个工程问题：
> **并发预约下的时段冲突控制**，以及**会议状态生命周期的一致性**。
> 后期又补了会议纪要：录音上传 COS、腾讯 ASR 转写、语音文本联动、DeepSeek 生成结构化纪要并导出 Word。

### 2.2 业务闭环（30 秒）

- 普通用户选会议室和时段 → 提交预约
- 需要审批的会议室 → 进入待审批；审批人通过/拒绝
- 到点自动进入进行中，结束自动完成
- 组织人可以改期、取消、延长、提前结束
- 全程站内信 + WebSocket 实时通知
- 会议结束后上传录音 → 自动转写 → 生成纪要 → 导出

### 2.3 项目规模（不要背太多数字，挑 3 个）

- 后端 4 个服务：gateway / auth / meeting / notification
- 数据库 20 张表；接口 61 个；错误码 46 个
- 后端单测 318（meeting-service 262，1 skipped）；前端 157；
  `verify-deploy` 15/15；纪要 E2E 11/11

## 三、架构与选型（2 分钟）

### 3.1 画图（白板/口述）

```text
浏览器 :8000
   │
 Nginx
   ├── /api/**        ──> gateway:8080 ──> auth-service:8081
   │                                     ├─> meeting-service:8082
   │                                     └─> notification-service:8083
   ├── /ws/**         ──> gateway:8080（WebSocket Upgrade）
   └── /files/local/** ──> meeting-service:8082（本地存储预签名）

4 个服务注册/发现：Nacos
数据：MySQL 8 / Redis 7 / RabbitMQ 3.13
```

### 3.2 为什么这么拆

| 决策 | 理由 | 代价/边界 |
|------|------|-----------|
| 微服务 | 按业务边界拆：认证、会议、通知；通知天然适合 MQ 解耦 | 单库、无分布式事务；用“本地事务 + AFTER_COMMIT 事件”避开 |
| Nacos | 服务发现 + 配置中心二合一；限流阈值可动态改 | 单机 standalone，生产需集群 |
| RabbitMQ | 会议事件 → 通知，削峰/解耦；手动 ACK + 死信 | 消息重复用 Redis SETNX 幂等 |
| Redis | 缓存、分布式锁、幂等、限流 | 锁和事务顺序要小心，锁必须包住事务 |
| 网关 | 统一 JWT 验签、身份头注入、CORS、WS 路由 | 内部服务只绑回环/内网，信任网关 |

### 3.3 一句话防追问

> 微服务不是为了“显得高级”，而是因为通知、认证、会议三条链路的**变更频率和故障边界**不同；
> 如果只是 CRUD，单体更合适。这个项目里真正需要拆的是“通知消费”和“认证”。

## 四、并发预约（3 分钟，招牌）

### 4.1 问题

同一会议室同一时段，多人同时提交，不能双重预订。

### 4.2 三层防护

1. **幂等**：`@Idempotent` + Redis SETNX，防同一请求重复提交
2. **分布式锁**：`lock:meeting:{roomId}:{date}`，Redisson，跨天逐日加锁
3. **锁内冲突检测**：半开区间 `[start, end)` 判重；含 buffer；锁内查库
4. **乐观锁**：修改会议用 `version`，防同一行并发覆盖

### 4.3 关键细节（面试官最爱追）

- **为什么锁 key 是“会议室 + 日期”**：锁粒度太粗（全局锁）吞吐差；太细（会议 ID）挡不住“新建 vs 改期”跨行竞态。
- **为什么锁必须包住事务**：用 `TransactionTemplate`，锁外开、事务锁内提交；
  不能用 `@Transactional` 包住锁，否则“锁释放 → 事务提交”之间有空窗。
- **为什么半开区间**：`10:00-11:00` 与 `11:00-12:00` 不冲突；闭区间会误判。
- **改期也要加同一把锁**：创建、改期、审批通过三条写路径都必须走同一把房间锁；
  漏一条就是双重预订的口子。修复前实测 **10 轮里 7 轮双重预订**。
- **幂等 key 清理**：参数错误时清理 key，允许重试；成功才保留。

### 4.4 演示动作（30 秒）

```bash
bash scripts/concurrent-reserve.sh 5
# 期望：5 并发抢同一时段，恰好 1 个成功，其余 40001 冲突
```

口述：这个脚本会自动登录、预检空闲时段、并发提交、断言成功数 = 1，可重复跑。

## 五、审批与状态机（2 分钟）

### 5.1 状态机

6 个状态（原系统 12 个，收敛理由：把“审批中/待开始/进行中/已结束/已取消/已拒绝”讲清楚即可）：

```text
10 待审批 → 20 待开始 → 30 进行中 → 40 已结束
     │           │
     ├─ 50 已取消 ┘
     └─ 60 已拒绝
```

- 迁移表驱动 + CAS 更新 + `meeting_status_log` 留痕
- 禁止裸 UPDATE 改 status
- 定时任务做兜底流转 + 对账补偿

### 5.2 审批的两个坑

1. **待审批不占时段**：`status=10` 的会议不计入冲突；
   否则“待审批”会把时段锁死，体验很差。
2. **审批通过必须复检**：通过时重新查冲突 + 加房间锁 + 会议室行锁；
   顺序固定“先会议室行 → 后会议行”，否则会和改期交叉持锁死锁。
   复检失败返回 50001 + 冲突详情，前端弹窗展示。

### 5.3 事件驱动

- 会议创建/审批/取消后发领域事件 → RabbitMQ → notification-service 落站内信 + WS 推送
- **必须在事务提交后发**：用 `TransactionSynchronization.afterCommit`；
  在事务内发，消费者可能读到未提交数据，回滚时消息已经发出去了
- 消费端：手动 ACK + Redis `SETNX mq:idem:{msgId}` 幂等 + 死信队列

### 5.4 演示动作（30 秒）

- 左屏 user1 提交梧桐厅预约（需审批）
- 右屏 approver1 通知中心 1 秒内 +1 → 点开待审批
- 审批通过；如果时段被抢，展示 50001 冲突详情

## 六、会议纪要（3 分钟）

### 6.1 链路

```text
浏览器选音频
  → 后端 initMultipart（5MiB 分片 + 预签名 URL）
  → 浏览器 3 并发直传 COS（不经过后端）
  → completeMultipart → file_object
  → POST /minutes/transcribe → 腾讯 ASR CreateRecTask
  → 定时任务 DescribeTaskStatus 轮询 → 解析分段 → 落库
  → 工作台：音频播放 + 转写逐句高亮联动
  → DeepSeek 异步生成结构化纪要（摘要/要点/决策/待办/风险）
  → 导出 Word
```

### 6.2 关键设计

- **COS 分片 + 断点续传**：3 并发、每片失败退避重试、`AbortController` 暂停、
  localStorage 记录 uploadId + completed，刷新后 listParts 续传
- **ASR 状态机**：`asr_status` 0/10/20/30/40；`asr_started_at` 作为 run token，
  重传/重试不会让旧任务覆盖新任务
- **ASR 分段格式**：`ResTextFormat=0`，解析 `[开始,结束,说话人] 文本` 行；
  比 `ResTextFormat=3` 的句级切分更接近原系统的“时间戳段落”体验
  （38 分钟会议：176 段，旧手工导入 181 段；句级切分曾产生 958 个碎段）
- **语音文本联动**：段内按标点切子句，按字符数比例估算时间；播放高亮当前子句，点击子句 seek；
  `@tanstack/react-virtual` 虚拟滚动，300 段只渲染十几行
- **音频编码坑**：Chrome 不支持 ALAC；上传前用 `<audio>` 元数据预检并拦截，
  提示转 AAC/M4A/MP3
- **AI 异步 worker**：DeepSeek JSON mode，超时/重试/卡死恢复；mock 与真实 provider 可切换

### 6.3 演示动作（60–90 秒）

- 打开 13556「审批123」→ 会议纪要
- 播放音频，点击转写子句，音频跳到对应时间
- 点“生成会议纪要”，展示摘要/待办/风险
- 点导出 Word，打开文件

> 如果现场网络不稳：用 compose 默认 `local + mock`，仍能完整演示上传、转写、联动、AI、导出；
> 真实腾讯 ASR/DeepSeek 作为“我实际联调过”的证据，不在现场赌网络。

## 八、高频追问（按主题）

### 8.1 并发与锁

**Q：为什么用 Redisson 而不是自己 SETNX？**
- 自己 SETNX 要处理锁续期、可重入、误删（value 校验 + Lua）、阻塞等待；
  Redisson 已经把这些做稳了。面试重点是“锁粒度 + 锁与事务顺序”，不是重复造轮子。

**Q：锁超时了但业务没执行完怎么办？**
- Redisson 看门狗续期；同时业务里避免长事务，锁内只做“查冲突 + 落库”。
- 如果进程崩溃，锁到期释放；状态机定时任务做兜底。

**Q：幂等和锁有什么区别？**
- 幂等解决“同一个请求重复提交”；锁解决“不同请求并发抢同一资源”。
- 两者都要：先幂等挡重复，再锁挡并发。

**Q：为什么不用数据库唯一索引直接防重？**
- 时段是区间，不是单值；唯一索引只能防完全相同的 start/end，
  挡不住交叉、包含、buffer 重叠。区间判重必须查库/锁内检测。

### 8.2 状态机与审批

**Q：为什么状态从 12 个收敛到 6 个？**
- 原系统很多状态是“展示态”而非“生命周期态”；收敛后迁移表更小、边界更清晰。
- 需要展示的细粒度信息放到状态日志/前端派生，不增加状态机复杂度。

**Q：待审批不占时段，会不会通过时发现被抢？**
- 会，所以审批通过必须复检；这是有意设计：待审批不锁资源，避免长期占用。
- 复检失败返回冲突详情，审批人可以选择拒绝或让用户改期。

**Q：AFTER_COMMIT 具体怎么实现？**
- `TransactionSynchronizationManager.registerSynchronization`，
  在 `afterCommit` 里发 MQ；发送失败只告警，不影响主事务（最终一致）。
- 消费端幂等 + 手动 ACK + 死信，保证“至少一次”不重复落库。

### 8.3 缓存与限流

**Q：缓存三大问题怎么处理？**
- 穿透：空值缓存 + 参数校验；击穿：逻辑过期/互斥重建；雪崩：TTL 加随机。
- 日历缓存是手写 key（按房间+周），会议室列表用注解式缓存。

**Q：限流为什么用 ZSET + Lua？**
- 滑动窗口比固定窗口平滑；Lua 保证“计数 + 判断 + 写入”原子。
- 阈值放 Nacos，改值不重启（`@RefreshScope`）。

### 8.4 会议纪要

**Q：为什么用预签名 URL 直传 COS？**
- 文件字节不经过后端，避免大文件占用 Tomcat 线程/内存；后端只负责签名和元数据。
- 分片 + 断点续传解决大文件和弱网。

**Q：ASR 任务重复/乱序怎么办？**
- `asr_started_at` 作为 run token；旧任务回来时 CAS 条件不满足，直接丢弃。
- 失败重试有次数上限；卡死任务由定时任务兜底。

**Q：为什么不用词级时间戳？**
- 词级时间戳数据量大、前端渲染成本高；当前段级 + 标点切子句已经够用。
- 如果要做：ASR 结果按词时间轴建索引，前端用二分查找当前词；文本按句子分组渲染，避免长列表。

**Q：DeepSeek 生成结果和转写不一致怎么办？**
- 之前踩过：运行环境是 mock provider，返回固定 fixture。
- 现在 `aiProvider` 透出到前端，页面显示“本地演示”；真实 provider 用 DeepSeek JSON mode，
  prompt 里带结构化转写，生成后做字段校验/重试。

### 8.5 部署与 CI

**Q：为什么 compose 默认 local + mock？**
- 冷启动零云密钥，面试演示不赌网络；真实 COS/ASR/DeepSeek 在 `.env` 切换。
- 真实腾讯 ASR 必须同时用 COS，因为腾讯需要公网可访问的音频 URL。

**Q：Nacos 容器 IP 怎么处理？**
- 容器内不能注册 `127.0.0.1`；设置 `SPRING_CLOUD_NACOS_DISCOVERY_IP=""`，
  Spring Cloud Alibaba 自动探测容器 IP。

**Q：服务容器重建后 Nginx 502 怎么办？**
- 用 `resolver 127.0.0.11` + 变量 `proxy_pass`，Nginx 会重新解析，不用重启 web。

**Q：CI 怎么保证不把本地密钥打进镜像？**
- `.dockerignore` 排除 `application-local.yml` / 嵌套 `.env`；
- Dockerfile 构建期 `find` 自检；CI 再扫描 jar 内是否含本地配置；
- 真实密钥只通过环境变量注入。

### 8.6 测试与质量

**Q：为什么 AuthFeignClientTest 不在 CI 默认套件？**
- 它的“auth 在线/离线”两个断言互斥，需要真实 auth-service；默认排除，按文档单独跑。
- 这是已知取舍，不是遗漏。

**Q：前后端测试怎么分工？**
- 前端 Vitest 只测纯逻辑（校验、几何、状态映射），不引 jsdom；
- 组件行为交给 Playwright E2E（真浏览器、真接口），避免两层重复投入。

## 九、三个“踩坑故事”（面试官最爱）

### 9.1 双重预订：10 轮里 7 轮

- 现象：并发测试偶尔出现两场会议同时占用同一时段。
- 根因：创建加了锁，但“改期”没有走同一把房间锁；乐观锁只管同一行，管不住跨行竞态。
- 修复：创建/改期/审批通过统一走房间锁 + 锁内检测 + 固定锁序。
- 结果：并发脚本 10 轮回归全部“恰好 1 个成功”。

### 9.2 ASR 958 个碎段

- 现象：38 分钟会议转写出 958 个极短分段，语音文本联动体验很差。
- 根因：`ResTextFormat=3` 走句级切分，粒度太细。
- 修复：改回 `ResTextFormat=0` 解析时间戳段落，得到 176 段，接近旧手工导入的 181 段。

### 9.3 多 tab 登录互相挤掉

- 现象：同一浏览器多个 tab 登录不同用户，后登录的把前一个挤掉。
- 根因：token 和用户快照都在 localStorage，同 origin 全 tab 共享。
- 修复：会话改存 sessionStorage，每 tab 独立；启动时迁移旧 localStorage 会话并清理共享副本。
- 边界：同一用户多 tab 仍只有一个 refreshToken，先登录 tab 到期需重登；不同用户已隔离。

### 9.4 部署 review 的 4 个 Critical

- 本地密钥配置可能被打进镜像；
- 嵌套 `.env` 未被 `.dockerignore` 排除；
- Nginx 默认访问日志会记录 WS token / 预签名 query；
- gateway/web 默认绑 `0.0.0.0` + 公开 JWT 默认值。

修复：`.dockerignore` + 构建期自检、日志只记 `$uri`、默认绑回环、
最小权限 DB 账号、CI 增加 jar 扫描。这个故事用来展示“我能接受 review 并收口”。

## 十、取舍与边界（主动说，显得可信）

| 取舍 | 原因 | 如果继续做 |
|------|------|-----------|
| 单库，无分布式事务 | 项目规模不需要；用本地事务 + AFTER_COMMIT 事件保证最终一致 | 按服务拆库，引入 outbox/事务消息 |
| 通知仅站内信 + WS | 邮件/短信不是核心链路 | 策略模式加 MailSender |
| 无词级时间戳 | 数据量和渲染成本高；段级 + 子句足够 | 词级索引 + 二分查找 |
| Compose 单机部署 | 面试演示足够；不是 K8s 项目 | Helm/K8s、TLS、集中日志 |
| 种子 admin/admin123 | 演示账号；默认只绑回环 | 首次登录强制改密、OIDC |
| ASR/AI 默认 mock | 现场网络不可控 | 真实 provider + 失败降级 |

## 十二、收尾话术（30 秒）

> 这个项目对我来说最大的收获不是“用了多少技术”，而是三件事：
> 第一，并发问题必须从锁粒度、锁与事务顺序、跨写路径三个层面一起看；
> 第二，状态机、幂等、事件驱动这些“一致性”手段要服务于业务边界，不是为了炫技；
> 第三，部署和 CI 是把项目从“能跑”变成“可交付”的分水岭——这也是我这次补得最晚、但收获最大的一块。
