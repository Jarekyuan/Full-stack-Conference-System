## 一、需求整理（技术视角）

### 1.1 功能需求 → 技术关注点

从 01 文档的功能模块（A~H）转译到技术视角，标记每个模块"技术上难在哪、用什么解决"：

| 模块 | 核心需求 | 技术关注点（难点） | 拟用技术 |
|------|---------|------------------|---------|
| A 认证与用户 | 登录、JWT、角色权限、用户搜索 | token 无感刷新、网关鉴权、线程上下文传递 | JWT 双 token + Redis、Spring Security ⏳、ThreadLocal |
| B 会议室管理 | CRUD、分组、策略配置、图片上传 | 写操作缓存一致性、文件存储、动态配置 | Spring Cache + 主动删除、MinIO/OSS、Nacos 配置 |
| C 预约管理 ★ | 创建（冲突检测+并发）、修改、延长、取消、日历查询 | **并发抢单、区间判重、幂等、重查询缓存** | Redisson、索引设计、AOP 幂等、Redis 缓存 |
| D 审批管理 | 待办、通过（复检）、拒绝 | 审批并发、状态机流转、异步通知 | 数据库锁/乐观锁、状态机、RabbitMQ |
| E 会议生命周期 | 状态流转、提醒、补偿 | 定时任务（多实例问题）、延迟消息 | Spring Task + Redisson、RabbitMQ 延迟消息 |
| F 周期会议 | 每周重复、系列取消 | 批量创建的一致性与冲突收集 | 事务 + 批量校验 |
| G 通知中心 | 站内信、未读、实时推送 | 跨服务异步解耦、消息可靠、推送 | RabbitMQ（可靠投递+幂等）、WebSocket |
| H 统计 | 使用率、个人统计 | 聚合查询、图表 | MySQL 聚合 + ECharts |

### 1.2 非功能需求 → 技术服务点

| 维度 | 要求（出自 01） | 技术手段 |
|------|---------------|---------|

## 二、总体架构方案 ⏳

> 本章为方案对比与决策记录。**8 项决策已于 2026-10-14 落定**（各节标 ✅，汇总见第十章）。

### 2.1 架构形态：三个方案对比

**你的技术清单里明确出现了 Nacos / OpenFeign / 网关 / 负载均衡——微服务是大概率方向。但先看全三者，再决策。**

#### 方案 A：单体分层（单个 Spring Boot 应用）

```
meeting-app（单进程）
 └─ controller / service / mapper / common（按包分层）
```

| 维度 | 评估 |
|------|------|
| 开发效率 | ★★★★★（一个进程，断点直达） |
| 部署成本 | ★★★★★（一个 jar，Docker Compose 简单） |
| 微服务技术覆盖 | ★☆☆☆☆（Nacos/Feign/网关 **无落点**） |
| 面试叙事 | "单体+讲清演进"（能讲，但手上没有实践证据） |
| 风险 | 无技术风险；但你的清单中 5+ 项技术无处落地 |

#### 方案 B：模块化单体（Maven 多模块，单进程）

```
meeting-app（单进程）
 ├─ app-web（启动+Controller）
 ├─ app-service（业务）
 ├─ app-dao（数据访问）
 └─ app-common（公共）
```

| 维度 | 评估 |
|------|------|
| 开发效率 | ★★★★☆ |
| 模块边界 | ★★★★☆（为将来拆分预留边界） |
| 微服务技术覆盖 | ★☆☆☆☆（同上，仍无 Nacos/Feign/网关落点） |
| 面试叙事 | "我做了模块化设计，为拆分做准备" |
| 风险 | 模块划分争议小；但**微服务技术仍是纸上谈兵** |

#### 方案 C：微服务（4 服务）★ 倾向方案

```
                      ┌──────────────────┐
  Web 前端 ──────────▶ │  gateway :8080    │  统一入口：JWT 鉴权 / 路由 / CORS / 限流 / traceId
                      └────────┬─────────┘
               ┌───────────────┼────────────────┐
               ▼               ▼                ▼
      ┌──────────────┐ ┌──────────────┐ ┌──────────────────┐
      │ auth-service │ │meeting-service│ │notification-service│
      │ :8081        │ │ :8082         │ │ :8083              │
      │ 认证/用户/权限 │ │ 会议室/预约/   │ │ 站内信/WebSocket/  │
      │              │ │ 审批/状态机/   │ │ 邮件(可选)         │
      │              │ │ 文件上传       │ │                    │
      └──────┬───────┘ └──────┬───────┘ └────────┬───────────┘
             │    ◀──Feign─── │                  │
             │                │ ────MQ─────────▶ │
             └────────────────┴──────────────────┘
                  Nacos（注册 + 配置中心）
        MySQL · Redis · RabbitMQ · MinIO（基础设施）
```

**拆分依据（面试必问："为什么这么拆"）**：
- `gateway`：所有流量入口，鉴权/限流/跨域是横切关注点，独立成层
- `auth-service`：**被所有服务依赖**（谁都要验证用户），且认证逻辑独立于业务演进——不能和业务绑一起
- `meeting-service`：核心业务域（会议室+预约+审批天然内聚——审批就是对预约的裁决）
- `notification-service`：**变化最频繁**（今天站内信、明天邮件、短信），且天然异步——解耦出去后，加渠道不需要动核心服务

| 维度 | 评估 |
|------|------|
| 开发效率 | ★★★☆☆（4 个进程 + 中间件，联调链路变长） |
| 部署成本 | ★★★☆☆（Nacos/RabbitMQ/Redis/MinIO/MySQL + 4 服务，Docker Compose 可一键） |
| 微服务技术覆盖 | ★★★★★（Nacos/Feign/LB/网关/配置中心全覆盖） |
| 面试叙事 | ★★★★★（拆分理由、服务间调用、网关鉴权、消息解耦全可讲） |
| 主要风险 | ①**过度设计质疑**："这么点业务为什么拆？"——需要准备回答（见 9.2）；②调试变复杂；③跨服务一致性问题（**设计上规避**：无跨服务强事务，通知走最终一致） |

#### 方案 D：渐进式演进（C 的单体起点版）

先按方案 C 的**模块划分**写成单体（4 个逻辑模块 → 1 个进程），M4/M5 再把 `notification` / `auth` 物理拆出、接上 Nacos + 网关。

| 维度 | 评估 |
|------|------|
| 优点 | 前期跑得快；**"先单体后拆分"本身就是最好的架构演进叙事**（比一开始就拆更能讲清"为什么拆"） |
| 缺点 | 需要多一轮重构；拆分时的代码搬迁有工作量 |

> ✅ **决策（2026-10-14）：采用方案 C——微服务 4 服务**。理由：真实企业微服务普及、与面试目标一致；技术清单中的微服务组件全部真实落地。
>
> ⚠️ 已知代价（准备应对）：4 进程 + 中间件使联调链路变长；"为什么拆"的追问必须准备充分（见 9.2 追问预案）。

### 2.2 认证方案对比 ⏳

| 对比项 | 方案 ①：Spring Security + JWT | 方案 ②：拦截器 + 自定义注解 |
|--------|------------------------------|---------------------------|
| 实现 | `OncePerRequestFilter` 解析 JWT → `SecurityContext` → `@PreAuthorize("hasRole('APPROVER')")` | `HandlerInterceptor` 解析 JWT → ThreadLocal → 自定义 `@RequireRole(ADMIN)` + AOP 校验 |
| 学习成本 | 高（Security 6.x 过滤器链、配置写法） | 低（拦截器你笔记里已有完整实践） |
| 面试标准性 | ★★★★★（"公司标配"，面试官熟悉） | ★★★☆☆（够用，但少了标准框架的深度对话） |
| 灵活性 | 方法级注解、表达式强大 | 自己控制，简单直接 |
| 与网关的关系 | 网关做 token 校验 + 服务内做细粒度方法鉴权（两层配合） | 网关校验 + 拦截器提取上下文 |
| 风险提示 | 配置繁琐，容易在 Security 6.x 的 API 变更上卡住 | 自研轮子的安全性要自己兜底（如路径匹配疏漏） |

> ✅ **决策（2026-10-14）：采用方案①——Spring Security + JWT**。面试标准性优先；①与网关的两层鉴权（网关验"你是谁"、服务内验"你能不能"）是主流配合方式。

### 2.3 限流方案（✅ 决策：不做全局限流）

| 对比项 | 方案 ①：Redis 业务限流（AOP + 滑动窗口） | 方案 ②：Sentinel（网关/服务层） | 方案 ③：Gateway 内置 RequestRateLimiter |
|--------|-------------------------------------|--------------------------|--------------------------------|
| 落位 | 预约创建接口（同一用户 5 次/分钟） | 网关层全局限流 + 服务熔断降级 | 网关按路由限流（Redis 令牌桶） |
| 业务语义 | ★★★★★（限"谁"很精确） | ★★★☆☆（偏基础设施指标） | ★★★★☆（IP/用户维度） |
| 学习成本 | 低（你笔记里有固定窗口实现，升级滑动窗口即可） | 高（控制台、规则配置、blockHandler） | 低（Gateway 内置） |
| 面试价值 | "业务限流怎么设计"（手写可深挖） | "微服务流控体系"（体系化，但可能被追问控制台细节） | "网关限流"（标准做法） |
| 风险提示 | 临界突刺要靠滑动窗口（ZSET）解决 | 组件带来额外部署成本 | 依赖 Redis，需处理 Redis 故障降级 |

> ✅ **决策（2026-10-14）——先承认一个前提：会议室预约系统没有高并发削峰场景**：
>
> - ❌ **不做网关全局限流**、不引入 Sentinel——为没有的流量加限流属于"为技术而技术"；
> - ✅ **保留唯一落点：预约创建接口的用户级防刷**（滑动窗口，如 10 次/分钟）。定位是"**防异常流量**"（脚本刷单/误操作）而非"限流抗并发"——属于接口健壮性设计，与系统 QPS 无关（原系统也只对预约接口做限流，侧面印证）；
> - 成本：AOP + Redis ZSet，半天内完成；定位 P1，**可整段删除而不影响主线**；
> - 讲述价值：固定窗口（临界突刺）→ 滑动窗口的演进选择（笔记 12 素材直接落位）。

### 2.4 数据库形态 ⏳

| 对比项 | 方案 ①：单库（多服务共库） | 方案 ②：按服务分库（auth / meeting / notification 各一库） |
|--------|--------------------------|-----------------------------------------------|
| 复杂度 | 低（一个 MySQL，表集中） | 中（三个库、连接配置×3、跨库查询消失——本来就不该有） |
| 真实性 | 演练够用（面试可讲"生产应分库"） | 与微服务"独立数据"原则一致，更真实 |
| 面试点 | "为什么拆服务不拆库？"（要有答案） | "独立库后怎么保证一致性？"（我答：不依赖跨库事务，用 MQ 最终一致） |
| 推荐 | **练手推荐①**（降低运维负担，设计上按归属分表前缀/注释标明），面试时讲清"生产会分" | 有精力时选② |

> ✅ **决策（2026-10-14）：采用方案①——单库**。按表归属逻辑划分（auth 表 / 会议表 / 通知表），面试讲清"生产会按服务分库"。

## 三、技术-业务映射（核心）

> 本章回答你的核心问题：**"每个技术应该加到哪个业务最合理，哪块真的适合吗"**。
> 判定标准：① 这个业务场景**真实存在**这个技术需求；② 加上后**业务收益 > 复杂度成本**；③ 面试时能讲清"为什么放这"。

### 3.1 后端技术落位总表

| # | 技术 | 落位业务 | 为什么放这（适配理由） | 面试考点 |
|---|------|---------|---------------------|---------|
| 1 | **Spring Boot 分层**（Controller/Service/Mapper + DTO/VO） | 全局 | 后端基座；DTO 收参/VO 出参分离防越权与信息泄露 | 分层职责、Entity/DTO/VO 区别（笔记 11 章） |
| 2 | **Nacos**（注册+配置中心） | 全局（服务发现 + 配置管理） | 微服务架构的"通讯录＋配置仓库"；把各服务配置收上去，演示 `@RefreshScope` 动态刷新（改限流阈值不重启） | 注册发现心跳机制、配置优先级（笔记 13 章） |
| 3 | **OpenFeign** | meeting-service → auth-service（**唯一真实场景**：创建预约时批量校验参会人存在性/查用户详情） | **不硬加**：全系统只有"会议域查询用户域"这一个真实的同步调用需求；通知走 MQ 不需要 Feign | 声明式调用原理、超时/重试/降级配置 |
| 4 | **Feign 降级（fallbackFactory）** | 同上（auth 服务不可用时：参会人校验 **降级为放行+告警**，不阻断预约主流程） | 核心链路不该被非核心依赖拖死——业务上"用户校验失败"宁可放过也不能阻塞预约 | 熔断降级策略、FallbackFactory vs Fallback |
| 5 | **负载均衡**（Spring Cloud LoadBalancer） | 全局（Feign 调用时自动选实例） | 演示：auth-service 起 2 个实例，Feign 轮询调用（印证笔记"内部负载均衡"） | 轮询/随机策略、与 Nginx 的分工（笔记 13 章★） |
| 6 | **Gateway 网关** | 全局入口 | 统一鉴权（白名单放行登录/刷新接口）、路由、CORS、traceId 注入、可选的限流 | GlobalFilter、lb:// 原理、鉴权为什么放网关（笔记 13 章） |
| 7 | **JWT + 无感刷新** | 模块 A（认证） | `accessToken(30min)` + `refreshToken(7d 存 Redis)`；401 自动刷新重放（见 5.1） | 双 token 设计理由、并发刷新处理、token 失效策略 |
| 8 | **Spring Security** ⏳ | 模块 A + 各服务方法级鉴权 | 网关校验"你是谁"，服务内 `@PreAuthorize` 校验"你能不能"（审批人/管理员接口） | 过滤器链、方法级鉴权、与拦截器的对比 |
| 9 | **ThreadLocal（用户上下文）** | 全局（每个服务） | 网关解析 JWT 后把 `userId/roles`（多角色数组）放请求头 → 服务内拦截器读头塞 ThreadLocal → Service/AOP 随处取（不层层传参） | 内存泄漏与 remove、**线程池复用串数据**（笔记 10 章★）、Feign 透传（拦截器把 ThreadLocal 塞进下游请求头） |
| 10 | **AOP：操作日志** | 预约/审批/会议室/用户管理的**写操作** | `@Log(type=XXX)` 注解 + 环绕通知：记录 who/when/what/result/耗时；**不侵入业务代码** | AOP 通知顺序、失效场景（自调用）、`@annotation` 切点（笔记 11 章） |
| 11 | **AOP：数据权限**（简化版 @IAuthority） | 会议操作（"只能操作自己的会议"） | 切面 + `@CheckOwner` 注解：反射取 meetingId → 校验 organiser/participant → 无权抛异常。**老系统精华的简化移植** ★ | 数据权限 vs 接口权限的区别（原系统踩坑叙事） |
| 12 | **AOP：接口幂等** | **创建预约接口** | `@Idempotent` + Redis SETNX（key=用户+方法+参数MD5），防用户双击重复提交 | 幂等方案对比（token/SETNX/唯一约束）、失败要删 key（笔记 11 章） |

## 五、核心业务流程（技术链路）

### 5.1 链路一：登录与 Token 无感刷新 ★

```
登录：
  前端 POST /auth/login {username, password}
   → Gateway：白名单放行 → auth-service
   → BCrypt 校验 → 签发 accessToken(30min) + refreshToken(7d，Redis 存 userId→token 映射)
   → 返回双 token → 前端存内存/localStorage（Zustand persist）

请求（正常）：
  前端带 Authorization: Bearer <accessToken>
   → Gateway JwtFilter：验签+过期判断 → 解析 userId/role 放请求头 X-User-Id → 转发
   → 目标服务拦截器：读头 → ThreadLocal.set → 业务处理

刷新（无感）：
  accessToken 过期 → 服务返回 401（或网关直接返回）
   → 前端 axios 响应拦截器捕获 401 → 调 /auth/refresh（带 refreshToken）
   → 换新 accessToken → 重放原请求（用户无感知）
   → 【并发刷新 single-flight】：多个请求同时 401 时，共享同一个 refresh Promise，
     只发一次刷新请求（前端经典考点 ★）
```

**面试追问预案**：refreshToken 也过期 → 跳登录；refreshToken 泄露 → Redis 可主动失效（删除即踢下线，JWT 无状态缺点的补丁）。

### 5.2 链路二：创建预约（全景链路）★

```
【前端】RHF 表单校验 → 生成幂等 token → POST /meetings
【Gateway】JWT 校验 → 限流（用户维度）→ traceId 注入 → 转发
【meeting-service】
  ├─ 1. 幂等检查：AOP @Idempotent → Redis SETNX(idem:{userId}:{token})
  ├─ 2. 参数校验：@Valid（时间合法性/标题长度）
  ├─ 3. 校验链（责任链模式）：
  │      基础校验 → 策略校验（提前天数/时长上限/窗口）→ 权限校验
  ├─ 4. Redisson 锁：lock:meeting:{roomId}:{date}（含跨天逐日加锁）
  ├─ 5. 冲突检测（锁内）：SELECT ... WHERE room_id=? AND status IN (20,30)
  │      AND start_time < :newEnd AND end_time > :newStart（半开区间）
  │      —— 冲突 → 返回冲突详情（含会议名/时间段/组织人）
  ├─ 6. 落库（本地事务）：meeting + participant + approval（如需）
  │      —— 状态：需审批→10 / 免审批→20
  ├─ 7. 事务提交后（@TransactionalEventListener AFTER_COMMIT）：
  │      发 MQ → meeting.created 事件
  └─ 8. 返回（会议 ID + 状态）
【notification-service】
  ├─ 消费 meeting.created → 幂等去重（msgId SETNX）→ 生成站内信
  └─ WebSocket 推送给在线用户
```

**注**：发送延迟消息（会议提醒）也在第 7 步一起发出（见 5.4）。

### 5.3 链路三：审批 & 延长（含并发防护）

```
审批通过：
  审批人 POST /approvals/{meetingId}/pass
   → 【悲观锁】SELECT ... FROM meeting WHERE id=? FOR UPDATE 锁定会议行（防两人同审）
   → 状态校验（必须为 10 待审批）
   → 【复检冲突】（锁内）：同 5.2 的冲突检测逻辑
        └─ 冲突 → 通过失败："时段已被占用" + 通知申请人
   → 状态机：10 → 20（transition 校验）→ 记录状态日志
   → 发 MQ：审批结果通知申请人+参会人

延长会议（ONGOING 特例）：
  组织人 POST /meetings/{id}/extend {minutes}
   → 计算上限：SELECT MIN(start_time) FROM meeting
        WHERE room_id=? AND status IN (20,30) AND start_time > :currentEnd
      maxDelay = min(下一场start − buffer, 当天24:00) − 当前end
   → 请求值 ≤ maxDelay → 冲突检测（缓冲区间）→ UPDATE end_time（乐观锁）
   → 发 MQ：通知参会人
```

### 5.4 链路四：会议提醒（延迟消息 vs 定时扫描对比）

| 方案 | 机制 | 优点 | 缺点/坑 |
|------|------|------|--------|
| ① 定时扫描 | Spring Task 每分钟扫"15 分钟后开始的会议" | 简单、无额外组件 | 精度受扫描间隔限制；频繁扫表有压力；多实例需分布式锁 |
| ② **MQ 延迟消息（推荐）** | 创建预约时发延迟消息（延迟 = 开始时间 − 15min） | 精准触发、分散压力、天然异步 | 需处理消息积压；TTL+DLX 有队头阻塞坑 |

**②的两种实现对比**（笔记 13 章的现成素材）：

| 实现 | 原理 | 坑 |
|------|------|-----|
| TTL + 死信交换机（DLX） | 消息在 delay 队列停留 TTL 后过期 → 进死信 → 路由到消费队列 | **队头阻塞**：不同 TTL 的消息在同一队列，先到的长 TTL 会阻塞后面的短 TTL（解决方案：按延迟时长分队列/单队列单延迟） |
| 延迟插件 `rabbitmq_delayed_message_exchange` | 插件原生支持任意延迟 | 需要安装插件（Docker 镜像可预置） |

> ✅ **采用（2026-10-14）**：**TTL+DLX**（"提醒提前量"固定 15 分钟 → 天然单一延迟，恰好规避队头阻塞）——原理讲得清、坑踩得明；插件方案作为对比储备。

### 5.5 链路五：状态流转与补偿

```
【每分钟】状态推进（Spring Task，条件更新天然幂等）：
  UPDATE meeting SET status=30 WHERE status=20 AND start_time <= NOW();   -- 开始
  UPDATE meeting SET status=40 WHERE status IN (20,30) AND end_time <= NOW();  -- 结束

【每小时】状态补偿（E-4）：扫描"状态与时间矛盾"的记录（异常数据修复 + 告警日志）
  例：status=20 但 start_time 已过 2 小时？（正常应被每分钟任务推进——
      出现说明任务中断/时钟异常，补偿任务兜底并记录审计）

【多实例问题】meeting-service 部署 2 实例时，两个 Spring Task 会重复执行：
  → 用 Redisson 锁互斥（task:meeting:status）+ 条件更新幂等双保险
  → 演示价值：起两个实例 → 观察日志 → 加锁修复（面试素材 ★）
```

### 5.6 链路六：日历查询（缓存链路）

```
GET /rooms/{id}/calendar?week=2026-10-13
 → meeting-service：
    1. 组装缓存 key：calendar:{roomId}:{weekStart}
    2. 查 Redis：
       命中 → 返回
       未命中 → 【互斥重建】Redisson 锁 single-flight
                → 查库（联合索引）→ 写缓存（TTL 5min + 随机抖动防雪崩）
    3. 空值处理：该周无会议 → 缓存空对象（短 TTL，防穿透）
 写入路径（预约/取消后）：
    → 事件监听 → 删除该会议室该周缓存（Cache-Aside：先更库后删缓存）
```

## 九、面试叙事增强

### 9.1 技术选型故事线（串成一个"为什么"链）

```
业务特点（会议室资源有限 + 预约有并发 + 通知要实时）
  ↓ 所以需要
并发控制 → 分层选锁（JVM → DB → 分布式），最终 Redisson + DB 兜底
  ↓ 为什么不用更重的
不引入 Seata/ES/分库分表——每个"不用"都有量化理由（见 3.2）
  ↓ 服务为什么拆
按"依赖方向 + 变化频率"拆 4 服务；通知走 MQ 保证解耦与最终一致
  ↓ 认证为什么这么设计
双 token + 网关鉴权 + 服务内方法级鉴权；无感刷新解决 30min 过期体验
```

### 9.2 预设追问与回答要点

| 面试官可能追问 | 回答核心要点 |
|--------------|-------------|
| "这点业务量为什么拆微服务？" | ①练手/演进模拟：按真实企业级形态设计（原系统 10 服务，我提炼 4 个）；②拆分依据是依赖方向与变化频率，不是"为拆而拆"；③每条链路我都做了简化（无跨服务事务、无分布式事务） |
| "拆了之后数据一致性怎么办？" | 设计上规避跨服务写：通知是异步最终一致（MQ 幂等消费）；强一致操作都在单服务单库本地事务内 |
| "锁 + 数据库约束，到底靠哪个？" | 双保险：锁防并发窗口内的竞态（性能好）；唯一约束/乐观锁兜底（正确性最后防线）。锁故障时数据不比错 |
| "为什么延迟消息不扫表？" | 扫表三大缺点（精度/压力/多实例重复）；但状态流转类仍用扫表——**两种方案按场景分工**才是完整答案 |
| "Redis 挂了预约怎么办？" | 降级：锁不可用 → 快速失败保正确性（或切数据库悲观锁兜底路径）；讲清可用性与正确性的取舍 |
| "前端怎么防重复提交？" | 前端按钮 loading + 后端幂等 token（双保险）；token 用 Redis SETNX + 过期 |
