## 一、项目真相源（防幻觉第一原则）

**写任何代码前，先找到它在文档里的出处。文档是唯一事实来源，不许凭记忆或"常见写法"臆造。**

| 你要做什么 | 先读哪里（真相源） |
|-----------|------------------|
| 接一个前端任务 | `docs/05-开发计划.md` 的 `T*.F*` 任务（五要素齐全） |
| 调后端接口 | `docs/04-接口设计.md`（路径/入参/响应结构/错误码——**不许自创字段名**） |
| 前端技术落位/组件清单 | `docs/02-技术架构方案.md` 3.3 / 3.4 节 |
| 页面结构与交互 | `docs/02-技术架构方案.md` 第四章 |
| 状态色/枚举展示 | `docs/04-接口设计.md` 第五章（状态 10-60 的配色已约定） |

**铁律**：① 文档与代码冲突时先停下报告；② 文档没写的细节列选项问用户；③ 不发明不存在的接口/字段/组件；④ 任务完成 = 验收标准全勾 + 验证命令实际通过。

## 二、技术栈基线（Vite SPA——注意：不是 Next.js！）

- **React 18** + **TypeScript（strict）** + **Vite**（纯前端 SPA，独立调用后端 API）
- UI：**antd 5**（组件）+ **Tailwind CSS**（布局与间距；分工：Tailwind 管"排版"，antd 管"组件"）
- 状态：**Zustand + immer**（客户端态：用户信息/UI 状态，persist 持久化）
- 请求：**axios**（封装实例）+ **ahooks useRequest 二次封装**（`useAppRequest`）
- 表单：**React Hook Form**；图表：**ECharts**；时间：**dayjs**；路由：**react-router**
- ⚠️ **禁止 Next.js 写法**：本项目没有 RSC / Server Actions / `next/*` 导入 / middleware.ts——若你想到的方案依赖 Next 特有能力，说明方案错了，回到 Vite SPA 视角重想。

## 三、目录与工程纪律

```
web/src/
├── api/          # 请求层：request.ts（axios 实例）+ 按业务分文件的接口封装（room.ts/meeting.ts...）
├── stores/       # Zustand：userStore / notificationStore 等（仅客户端状态）
├── hooks/        # useAppRequest / useWebSocket / usePermission / useDebounce...
├── pages/        # 路由页面（Calendar / MeetingList / ApprovalCenter / admin/*...）
├── components/   # 业务组件（RoomPicker / UserPicker / MeetingStatusTag...）
└── layouts/      # MainLayout 等骨架
```

- **所有请求必须走 `src/api/`**：组件内不许直接 axios / fetch；token 注入、401 刷新、统一错误处理全部收在 `request.ts` 拦截器里（含 **401 single-flight 刷新**，见 02 文档 5.1）
- **服务端数据用 `useAppRequest`**：组件不手写 loading/error/刷新状态机；`refreshDeps` 处理"参数变化自动重查"（如日历切周）
- **状态分工**：只有**客户端全局状态**才进 Zustand；接口数据不放进 store（避免两处真相）
- **组件纪律**：函数组件 + Hooks；单文件超 300 行考虑拆分；可复用业务组件下沉到 `components/` 并给出 props 类型
- **TypeScript**：禁止 `any`（用 `unknown` + 类型收窄）；接口类型以 04 文档为准手写/派生，不臆造

## 四、常用命令

```bash
cd web
npm install           # 安装依赖（仓库规范是 pnpm，但本机 pnpm 建 node_modules 会失败，见下）
npm run dev           # 开发服务 :5173（已配置代理 /api → :8080）
npm run build         # 生产构建（tsc --noEmit + vite build）
npm run tsc           # 类型检查
```

> ⚠️ **包管理器现状（2026-10-14）**：规范仍是 pnpm、不用 npm/yarn，但本机在 WorkBuddy
> 的文件系统代理层下，pnpm 的 `symlinkAllModules` / `importPackage` 会随机报
> `ENOENT`/`EEXIST`（并发 symlink 与 tmp+rename 竞态），实测连续 5 次都装不完。
> 因此本轮改用 npm 安装（依赖清单与脚本不变，仅换包管理器），现状记录在 `web/.npmrc`。
> 如果你在自己的终端里 `pnpm install` 能成功，用 pnpm 即可——**但不要同时提交两份 lockfile**。

## 五、行为指南

1. 先思考，后编码
   不要想当然。不要掩饰困惑。要暴露权衡。
- 明确陈述你的假设。如果不确定，请提问。
- 如果存在多种解释，请列出它们——不要暗自挑选。
- 如果存在更简单的方法，请指出来。在有充分理由时提出反对意见。
- 如果某些内容不清楚，请停下来。指出令人困惑的地方。并提问。
2. 简单至上
   解决问题所需的最少代码。不要写推测性的代码。
- 不要为一次性使用的代码添加抽象层。
- 不要为不可能发生的场景编写错误处理。
- 如果你写了 200 行代码而 50 行就够了，请重写。
- 问问自己："资深工程师会认为这过于复杂吗？" 如果是，请简化。
3. 精准修改
   只改动必须改的地方。只清理自己造成的混乱。
   在编辑现有代码时：
- 不要"改进"周围的代码、注释或格式。
- 不要重构没有问题的东西。
- 保持与现有风格一致，即使你个人偏好不同。
- 如果你注意到不相关的死代码，可以提出来——但不要删除它。
4. 目标驱动执行
   定义成功标准。循环验证，直到达标。
- "修复那个 bug" → "编写能复现该 bug 的测试，然后让测试通过"。
- "重构 X" → "确保重构前后测试都能通过"。
- 对于多步骤任务，陈述简要计划，按 [步骤] → 验证方式：[检查点]来执行。

- 解释代码时简洁直接，不要啰嗦
- 使用组件化、模块化、工程化的思想
- 需要确认的操作（删除、清空数据等）先征求同意，不直接执行
- 修改超过 50 行的代码时，先展示改动计划
- 不确定的技术选型和解决方案，先列出方案对比而非直接选择
